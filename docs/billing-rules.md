## เลขตั้งต้นที่ใช้คิดหน่วยน้ำ

`getPreviousUnit()` เป็น **จุดเดียวในระบบที่ตัดสินเรื่องนี้** ทั้งหน้าจอและตอนออกบิลจริงเรียกตัวเดียวกัน ตัวเลขบนจอกับยอดที่ออกจริงจึงตรงกันเสมอ

| ลำดับ | แหล่ง                                            | `source`         |
| ----- | ------------------------------------------------ | ---------------- |
| 1     | เลขปิดของบิลใบล่าสุดที่เดือนเก่ากว่า             | `'bill'`         |
| 2     | เลขมิเตอร์ ณ วันลงทะเบียนบ้าน (การจดครั้งแรกสุด) | `'registration'` |
| 3     | ไม่มีทั้งคู่ → 0                                 | `'none'`         |

กฎชุดนี้อยู่ใน `resolvePreviousUnit()` ซึ่งรับข้อมูลที่โหลดมาแล้วเข้าไปตรง ๆ ไม่ยิงคิวรีเอง ทั้งแบบรายบ้าน (`getPreviousUnit`) และแบบยกชุด (`previousUnitsForMembers` ที่ scan-batch ใช้) จึงใช้กฎเดียวกันจริง ๆ

## ด่านกันข้อมูลผิดตอนออกบิล

ทั้งหมดอยู่ใน `bills.service.ts` และทำงานก่อนเขียนฐานข้อมูลเสมอ — `prepareBill()` ตรวจให้จบก่อน แล้วค่อยเขียนทั้ง `meter_readings` และ `bills` ในทรานแซกชันเดียว

| เคส                                          | เกิดอะไรขึ้น                                                          |
| -------------------------------------------- | --------------------------------------------------------------------- |
| เลขมิเตอร์น้อยกว่าเลขตั้งต้นเดือนก่อน        | 400 — บอกทั้งเลขที่จดและเลขตั้งต้น พร้อมทางออกเรื่องเปลี่ยนมิเตอร์    |
| เปลี่ยนมิเตอร์ใหม่ / มิเตอร์วนรอบ 99999→0    | กด `confirm_meter_reset` ผ่านได้ เริ่มนับจาก 0 ให้                    |
| หน่วยน้ำสูงผิดปกติ                           | 409 ต้องกด `confirm_high_usage` ยืนยัน ไม่บล็อกตาย                    |
| **จำนวนหลักบนหน้าปัดไม่ตรงกับที่เคยอ่านได้** | 409 ต้องกด `confirm_digit_change` — จับ OCR อ่านหลักหาย/เกิน          |
| **OCR อ่านไม่ชัด (`read_confidence` < 0.85)** | 409 ต้องกด `confirm_low_confidence` — จับ OCR อ่านผิดค่าโดยหลักไม่เปลี่ยน |
| **`captured_at` ซ้ำกับการจดที่มีอยู่** | 409 **บล็อกตาย ไม่มีปุ่มยืนยัน** — ไฟล์รูปเดิมถูกอัปซ้ำแน่นอน |
| พิกัดตรงเป๊ะทุกทศนิยมกับการจดที่มีอยู่ | 409 ต้องกด `confirm_duplicate_location` — GPS ไม่เคยให้ค่าเดิมซ้ำ |
| รูปถ่ายห่างจากวันจดเกิน 30 วัน | 409 ต้องกด `confirm_stale_photo` — รูปเก่า ไม่ใช่แค่นาฬิกากล้องเพี้ยน |
| ออกบิลซ้ำเดือนเดิม                           | 409 ต้องกด `replace` จดทับ — ถ้าบิลนั้นจ่ายแล้วห้ามทับเด็ดขาด         |
| ออกบิลย้อนหลังทับหน้าใบที่ใหม่กว่า           | 409 ต้องลบใบที่ใหม่กว่าก่อน (ไม่งั้นใบใหม่จะมีเลขตั้งต้นผิดทันที)     |
| เดือน/ปีของบิลไม่ใช่ 01-12 หรือปีเพี้ยน      | 400 — ถ้าปล่อยผ่าน `monthKey()` จะได้ `NaN` แล้วด่านเทียบเดือนหลุดหมด |
| `reading_date` อ่านไม่ออก / เป็นอนาคต        | 400                                                                   |
| `reading_date` ห่างจากเดือนบิลเกิน 15 วัน    | 400 ให้แก้วันที่จด หรือเปลี่ยนเดือนบิลให้ตรงกัน                       |
| พิกัดนอกช่วง (พิมพ์ผิด / สลับ lat-lng)       | 400 — ไม่ปล่อยไปพังที่ MySQL เป็น error 1264                          |
| `captured_at` ที่ไม่ใช่วันที่                | ถือเป็น `null` ไม่บล็อก (เป็นข้อมูลประกอบ ไม่มีผลต่อยอดเงิน)          |
| ลบบิลที่ `Paid` แล้ว                         | 409 — ลบแล้วหายทั้งบิล การจดมิเตอร์ และไฟล์รูปหลักฐาน กู้ไม่ได้       |
| ไม่แนบรูปมิเตอร์ (เลขมาจาก OCR)              | ออกบิลได้ปกติ — รูปเป็น optional                                      |
| **กรอกเลขเอง (`entry_method: manual*`) แล้วไม่แนบรูป** | 400 **บล็อกตาย ไม่มีปุ่มยืนยัน** — ดูหัวข้อข้างล่าง |
| **เวลาถ่าย (`captured_at`) เป็นอนาคต** | 400 **บล็อกตาย** — นาฬิกาเครื่องเพี้ยน ต้องตั้งให้ตรงก่อน |
| **ถ่ายรัวจากจุดเดิม (< 3 วิ และขยับ < 5 ม.)** | 409 **บล็อกตาย** — ยืนที่เดิมกดชัตเตอร์ ไม่ใช่เดินไปถ่ายอีกมิเตอร์ |
| ถ่ายค้างไว้เกิน 24 ชม. ก่อนส่งเข้าระบบ | ผ่าน — ติดธง `stale_photo` ไว้เฉย ๆ (offline mode ทำแบบนี้เป็นปกติ) |

**กรอกเลขเองต้องมีรูปเสมอ ไม่มีปุ่มยืนยัน** — ด่านอื่นเปิดปุ่มยืนยันไว้เพราะยังมีข้อมูลอีกชิ้นให้คนตรวจใช้ตัดสิน (รูป, ประวัติ, จำนวนหลัก) แต่เลขที่กรอกมือแล้วไม่มีรูป**ไม่เหลืออะไรให้ตรวจเลยแม้แต่ชิ้นเดียว** — ทั้งระบบต้องเชื่อตัวเลขที่พิมพ์มาล้วน ๆ ซึ่งเป็นสภาพเดียวกับการจดมือลงสมุดที่โปรเจกต์นี้ตั้งใจแก้ตั้งแต่ต้น ปุ่มยืนยันตรงนี้จึงไม่มีความหมาย เพราะคนที่กดคือคนเดียวกับที่พิมพ์เลขมา

**ไม่ประกาศ `entry_method` มา** ระบบเดาจากว่ามีค่า `read_confidence` ติดมาไหม — หน้าเว็บรุ่นเก่าที่ยังไม่ส่งฟิลด์นี้จึงทำงานได้เหมือนเดิม

**"สูงผิดปกติ" คิดจาก** — เทียบ **หน่วยต่อเดือน** (`usage_unit ÷ period_months`) กับเกณฑ์ **สองชั้น**:

| ชั้น | เกณฑ์ (ค่ากลาง) | เกิดอะไรขึ้น | ตั้งค่ารายหมู่บ้าน |
| --- | --- | --- | --- |
| เตือน | `> baseline × 2` และ `> 50 หน่วย` | ติดธง `usage_warning` **ไม่บล็อก ไม่ต้องกดอะไร** | `villages.usage_warn_ratio` |
| บล็อก | `> baseline × 5` และ `> 50 หน่วย` | 409 ต้องกด `confirm_high_usage` | `villages.usage_spike_ratio` |
| บ้านใหม่ | `> 1000 หน่วย` ตายตัว | 409 ต้องกด `confirm_high_usage` | — (เพดานระบบ) |

**ทำไมไม่เอาเกณฑ์ 2 เท่ามาบล็อกไปเลย** — หน่วยน้ำเกินสองเท่าเกิดขึ้นจริงเป็นปกติ (หน้าร้อนรดน้ำต้นไม้, ญาติมาพัก, ล้างรถครั้งใหญ่) บล็อกที่ระดับนี้เจ้าหน้าที่จะเจอหน้าต่างยืนยันแทบทุกใบแล้วกดผ่านเป็นนิสัย — ซึ่งทำให้ด่านที่ 5 เท่าพลอยไร้ความหมายไปด้วย เพราะมือกดไปก่อนตาอ่านเสมอ

ชั้นเตือนจึงมีไว้ตอบคำถามคนละข้อ: "เดือนนี้บ้านไหนใช้น้ำขยับบ้าง" ซึ่งเอาไปไล่ดูย้อนหลัง (เช่นหาท่อรั่ว) ได้ที่ `GET /audit/flags?flag_type=usage_warning` โดยไม่ต้องรบกวนคนที่กำลังเดินจดอยู่หน้างาน

`usage_spike_floor` ตั้งรายหมู่บ้านได้เหมือนกัน (ค่ากลาง 50 หน่วย)

`usageBaseline()` = **median ของบิล 6 เดือนล่าสุด** ไม่ใช่ค่าเฉลี่ยของทุกใบ เพราะของเดิมมีปัญหาสองชั้นทับกัน:

1. ค่าเฉลี่ยถูกลากด้วยค่าโดด — บ้านที่ท่อแตกครั้งเดียว 400 หน่วยจะดันเกณฑ์ขึ้น **ถาวร** ด่านอ่อนลงทุกเดือนหลังจากนั้น
2. ยิ่งใช้งานนานยิ่งมีบิลเยอะ ค่าเฉลี่ยยิ่งขยับยาก ด่านที่ควรแม่นขึ้นตามข้อมูลกลับด้านลงเรื่อย ๆ

median ทนค่าโดดโดยธรรมชาติ และการตัดที่ 6 เดือนทำให้เกณฑ์ตามพฤติกรรมปัจจุบันของบ้านหลังนั้นจริง ๆ (แนวเดียวกับที่ `learnedMeterLocations` ใช้ median กับพิกัด)

`ScanBatchService` ต้องใช้ `BillsService.usageBaseline()` ตัวเดียวกัน ไม่งั้นหน้าอัปรูปจะเสนอบ้านที่พอกดยืนยันจริงแล้วโดนตีกลับเป็น 409

**การหารด้วย `period_months` สำคัญ** — บิลที่คาบ 2 เดือน (เพราะเดือนก่อนไม่ได้ไปจด) มีหน่วยน้ำเป็นสองเท่าโดยธรรมชาติ ถ้าเทียบตัวเลขดิบจะเด้ง 409 ทั้งที่เลขถูกทุกอย่าง แล้วคนก็จะชินกับการกดผ่าน — ซึ่งทำให้ด่านนี้ไร้ความหมายในวันที่เลขผิดจริง

**ด่านจำนวนหลักทำงานยังไง** — มิเตอร์ตัวเดิมมีจำนวนหลักคงที่ตลอดอายุการใช้งาน ระบบเทียบ `meter_digits` ที่ OCR ส่งมากับค่าที่บ้านหลังนี้เคยอ่านได้ล่าสุด ต่างเมื่อไหร่แปลว่าอ่านหลักหายหรือหลักเกิน

ด่านนี้ **ไม่พึ่งประวัติการใช้น้ำเลย** จึงจับเคสที่ด่านหน่วยพุ่งปล่อยผ่านได้ — บ้านที่ยังไม่มีบิลใช้เพดาน 1,000 หน่วยซึ่งหลวมพอให้เลขที่เกินมาหนึ่งหลักลอดไปได้ และบ้านที่ปกติใช้เยอะอยู่แล้วเพดาน "เฉลี่ย × 5" ก็สูงตามไปด้วย

จำนวนหลักนับจาก **string ดิบ** ก่อนแปลงเป็นตัวเลข — `00025` คือ 5 หลัก ไม่ใช่ 2 เพราะศูนย์นำหน้าคือหลักที่มีอยู่จริงบนหน้าปัด ถ้านับจากตัวเลขที่แปลงแล้วค่าจะเปลี่ยนไปมาตามที่มิเตอร์เดินไปถึง แล้วเทียบข้ามเดือนไม่ได้เลย

ไม่ส่ง `meter_digits` มา (กรอกเลขเอง ไม่ได้ผ่าน OCR) จะข้ามด่านนี้ไป — คอลัมน์เก็บเป็น `NULL` และไม่ถูกนับเป็นค่าอ้างอิงของเดือนถัดไป

**เปลี่ยนมิเตอร์แล้วน้ำที่ใช้ก่อนถอดไปไหน** — วิธีที่ควรใช้คือบันทึกผ่าน `POST /meters/replace` **ตอนที่เปลี่ยนจริง** แล้วบิลใบถัดไปจะบวกหน่วยค้างให้เอง ไม่ต้องมีใครจำ

ทำไมต้องบันทึกตอนเปลี่ยน ไม่รอกรอกตอนออกบิล — คนที่เปลี่ยนมิเตอร์ (ช่าง) กับคนที่เดินจดรอบถัดไปมักคนละคนและห่างกันเป็นสัปดาห์ คนจดจึงไม่มีทางรู้เลขปิดของตัวที่ถอดไปแล้ว ถ้ารอให้กรอก หน่วยก้อนนั้นจะหายเงียบ ๆ ทุกครั้งที่เปลี่ยนมิเตอร์

ระบบหยิบจาก `meters` ที่ `removed_at` ไม่ว่างและ `residual_billed_at` ยังว่าง แล้ว **มาร์กว่าคิดแล้ว** ทันทีในทรานแซกชันเดียวกับบิล — ขาดการมาร์กนี้ไม่ได้ ไม่งั้นหน่วยก้อนเดิมจะถูกบวกเข้าไปในบิลทุกใบหลังจากนั้น (เก็บซ้ำทุกเดือนจนกว่าจะมีคนสังเกต)

ยังส่ง `old_meter_final_unit` มากับ `POST /bills/scan` ได้เหมือนเดิม และ **ค่าที่ส่งมาชนะทะเบียนเสมอ** เพราะคนที่ยืนอยู่หน้ามิเตอร์เห็นของจริง ไม่ส่งและไม่มีทะเบียนก็คิดเฉพาะมิเตอร์ตัวใหม่ — คิดขาดดีกว่าคิดเกิน เพราะลูกบ้านเป็นฝ่ายจ่าย

## ทบยอดค้างเข้าบิลเดือนถัดไป

| คอลัมน์ | คืออะไร |
| --- | --- |
| `total_amount` | **ค่าน้ำของเดือนนี้เท่านั้น** — ห้ามเอายอดค้างมาปนเด็ดขาด |
| `arrears_amount` | ยอดค้างสะสมที่ทบเข้ามา (ภาพนิ่ง ณ วันออกบิล) |
| `grand_total` | `total_amount + arrears_amount` = ตัวเลขที่พิมพ์บนใบเสร็จ |
| ตาราง `bill_arrears` | ใบใหม่ทบยอดของใบเก่าใบไหนมาบ้าง (รายใบ ไม่ใช่แค่ยอดรวม) |

**ทำไมห้ามบวกเข้า `total_amount`** — `usageBaseline()`, `outstandingByMember()` และรายงานรายได้อ่านคอลัมน์นั้นว่าเป็นค่าน้ำของรอบเดียว การเอายอดเก่าไปปนทำให้ยอดค้างถูกนับซ้ำทุกเดือนที่ทบต่อกันไป

**ต้องรับเงินด้วย `POST /bills/:id/pay` เท่านั้น** — คำสั่งนี้ปิดใบเก่าทุกใบใน `bill_arrears` ให้เป็น `Paid` ในทรานแซกชันเดียวกัน ถ้าไปกด `PATCH /bills/:id/status` แทน ใบเก่าจะยังค้างอยู่ แล้วบิลเดือนถัดไปจะทบยอดเดิมเข้าไปอีกรอบ = ลูกบ้านโดนเก็บซ้ำจากก้อนที่จ่ายไปแล้ว

**`GET /bills/outstanding` ยังรวมจาก `total_amount` เหมือนเดิม** — ห้ามเปลี่ยนไปรวม `grand_total` เพราะจะนับยอดค้างซ้ำทันที

## ย้ายเข้า-ย้ายออกกลางเดือน — `POST /tenancies/move-out`

จดมิเตอร์ครั้งสุดท้าย → ออกบิลปิดยอด → ปิดสัญญา ในคำสั่งเดียว บิลที่ได้ต่างจากบิลประจำเดือนสองอย่าง:

1. **`due_date` = วันย้ายออกเลย** ไม่ยืดตาม `payment_due_days` — รอบชำระปกติตั้งอยู่บนสมมติฐานว่าคนยังอยู่บ้านหลังนั้น แต่คนที่ย้ายออกไปแล้วตามเก็บแทบไม่ได้ ยอดต้องเคลียร์ ณ วันที่ยังเจอตัวกันอยู่
2. **ทบยอดค้างเก่าทั้งหมดเข้าใบนี้** เพราะเป็นใบสุดท้ายที่เรียกเก็บจากคนนี้ได้ ไม่ทบก็ตกไปอยู่กับผู้เช่าคนถัดไปที่ไม่ได้ใช้น้ำก้อนนั้นเลย

**ผู้เช่าคนใหม่ไม่ต้องตั้งเลขตั้งต้นเอง** — `getPreviousUnit()` หยิบเลขปิดของบิลใบล่าสุด (`source: 'bill'`) อยู่แล้ว ซึ่งคือเลข ณ วันย้ายออกพอดี

ปิดสัญญา **หลัง** บิลออกสำเร็จเท่านั้น — ปิดก่อนแล้วบิลตกด่านจะเหลือบ้านที่ไม่มีผู้อยู่อาศัยทั้งที่ยังไม่ได้เคลียร์ยอด แล้วไม่มีใครรู้ว่าต้องไปตามใคร

## ธงสอบทาน (`reading_flags`)

ทุกครั้งที่กดปุ่ม `confirm_*` ผ่านด่าน ระบบเขียนแถวลง `reading_flags` **ในทรานแซกชันเดียวกับบิล** — ก่อนหน้านี้การกดข้ามด่านไม่เหลือหลักฐานเลย ระบบจึงตอบไม่ได้ว่าเดือนที่แล้วมีใครกดข้ามด่านไหนไปกี่ครั้ง

| Endpoint | ตอบอะไร |
| --- | --- |
| `GET /audit/flags?flag_type=&members_id=` | รายการธง พร้อมบ้านและวันที่จด |
| `GET /audit/flags/summary?days=30` | นับแยกตามชนิด + จำนวนที่คนกดยืนยันเอง |

⚠️ **ธงใบเดียวแทบไม่ได้แปลว่ามีอะไรผิด** — พิกัดซ้ำครั้งเดียวเกิดจากหน้าเว็บ cache พิกัดไว้ก็ได้ สิ่งที่บอกอะไรจริงคือ **ความถี่ต่อคน**

ถ้าธงชนิดไหนขึ้นเกือบทุกใบ แปลว่าเกณฑ์ตั้งแน่นเกินของจริง — ให้ปรับ `villages.usage_spike_ratio` ไม่ใช่ปล่อยให้คนกดผ่านต่อไป เพราะนิสัยกดผ่านจะลามไปถึงใบที่ผิดจริง

**ลบบิล / ลบบ้าน จะเก็บกวาดไฟล์รูปให้ด้วย** — ลบทีหลัง commit สำเร็จเสมอ เพราะการลบไฟล์ย้อนกลับพร้อม rollback ไม่ได้

## กำหนดชำระและการติดตามหนี้

**`due_date` = วันจดมิเตอร์ + `villages.payment_due_days`** (ไม่ตั้งค่า = 15 วัน)

นับจากวันจด ไม่ใช่วันที่ 1 ของเดือนบิล เพราะลูกบ้านเริ่มรู้ยอดตอนที่พนักงานไปจดถึงหน้าบ้าน — จดวันที่ 28 แล้วให้ครบกำหนดวันที่ 15 ของเดือนเดียวกันเท่ากับเลยกำหนดตั้งแต่วินาทีที่ออกบิล

**`markOverdue()` ดีดสถานะให้เอง** ไม่ต้องมีใครกดเปลี่ยน — เรียกอัตโนมัติก่อนอ่านรายการบิลทุกครั้ง (`findAll` / `findAllForMembers` / `findOne` / `outstanding`) **และตี 1 ทุกคืนจาก cron** (`HousekeepingService.markOverdueBills`)

สองทางนี้ทำงานทับกันได้ไม่มีปัญหา (คิวรีเดียวกัน แตะเฉพาะแถวที่เข้าเงื่อนไข `Pending` + `due_date < CURDATE()`) ที่ต้องมี cron เพิ่มเพราะระบบแจ้งเตือนต้องอ่าน "สถานะที่ถูกต้อง ณ วันนี้" โดยไม่มีใครเปิดหน้าเว็บก่อน ซึ่งการอัปเดตตอนอ่านอย่างเดียวทำไม่ได้

**ไม่แตะบิลที่ `due_date` เป็น `NULL`** — บิลเก่าก่อน migration ไม่มีกำหนดชำระที่เชื่อได้ การดีดเป็น `Overdue` ยกล็อตจะกลบภาพว่าใบไหนค้างจริง

| Endpoint | ตอบอะไร |
| --- | --- |
| `GET /bills/outstanding?villages_id=` | ยอดค้างสะสม**รายบ้าน** — รวมทุกใบที่ยังไม่จ่ายเป็นยอดเดียว พร้อมจำนวนใบ / จำนวนใบที่เลยกำหนด / วันครบกำหนดที่เก่าที่สุด เรียงบ้านที่ค้างหนักสุดขึ้นก่อน |
| `GET /bills/missing?month=&year=&villages_id=` | บ้านที่**ยังไม่มีบิล**ของเดือนนั้น พร้อม `months_since_last_bill` ที่แยกบ้านที่แค่ยังไม่ได้จดรอบนี้ (= 1) ออกจากบ้านที่หายไปหลายเดือน |

`/bills/missing` ต้องเปิดดูตั้งแต่ยังอยู่ในเดือนนั้น — ถ้าปล่อยจนข้ามเดือน หน่วยที่ตกหล่นจะไปโผล่รวมกับเดือนถัดไป (`period_months` = 2) ซึ่งย้อนกลับไปจดไม่ได้แล้ว

## ลงทะเบียนบ้านแบบยืนที่มิเตอร์ — `POST /member/register-onsite`

ของเดิม (`POST /member/create`) กรอกฟอร์มจากที่ทำการ ทำให้เกิดปัญหาสองอย่าง:

1. พิกัดในทะเบียนคือกลางหลังคา แต่ตอนจดมิเตอร์พนักงานยืนริมรั้ว — เหลื่อมกัน 10–15 ม. ทุกครั้ง แยกบ้านไม่ออก
2. **ไม่เคยบันทึกเลขมิเตอร์ตั้งต้น** → บิลใบแรกคิดจาก 0 บ้านที่มิเตอร์เดินมาแล้ว 800 หน่วยก่อนเข้าระบบจะโดนเก็บย้อนหลังทั้งก้อนโดยไม่มีใครเตือน

แบบใหม่บันทึกตอนยืนอยู่หน้ามิเตอร์จริง แก้ทั้งสองข้อพร้อมกัน — สร้างทั้ง `members` และการจดครั้งแรกใน `meter_readings` ในทรานแซกชันเดียว การจดครั้งแรกนี้คือสิ่งที่ `getPreviousUnit()` มองหาเป็นลำดับที่ 2 (`source: 'registration'`) อยู่แล้ว

**ด่านตรวจ:**

- ต้องส่งพิกัดมาเสมอ (ไม่ใช่ optional เหมือนของเดิม) และต้องมาจาก `navigator.geolocation` ตอนยืนอยู่จริง ห้ามจิ้มจากแผนที่
- `gps_accuracy_m > 20` → ปฏิเสธ ให้รอสัญญาณนิ่งแล้วกดใหม่ (พิกัดที่ห่วยกว่านั้นรับไว้ก็ไปทำให้ค่ามัธยฐานเพี้ยน แล้วหลอกให้ระบบคิดว่ามีพิกัดอ้างอิงทั้งที่ใช้จริงไม่ได้)
  เข้มกว่าตอนจดมิเตอร์เพราะค่านี้เป็น **จุดอ้างอิง** ที่การจดทุกครั้งจะถูกเทียบเข้าหา ความคลาดเคลื่อนเลยบวกกันสองชั้น: √(20² + 30²) ≈ 36 ม. ยังอยู่ใน `GPS_NEAR_M` (50 ม.) แต่ถ้าปล่อยไว้ที่ 50 จะได้ ≈ 58 ม. ซึ่งเกินไปแล้ว — ยอมเข้มได้เพราะวัดครั้งเดียวต่อบ้าน ยืนรอสัญญาณนิ่งได้
- `initial_meter_unit` ต้องเป็นจำนวนเต็มไม่ติดลบ
- บ้านเลขที่ห้ามซ้ำ
- รูปหลักฐานเขียนลงดิสก์ก่อนเข้าทรานแซกชัน ถ้าทรานแซกชันล้มจะลบไฟล์ทิ้งให้ (การเขียนดิสก์ย้อนกลับพร้อม rollback ไม่ได้)
