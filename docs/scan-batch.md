# จับคู่รูปกับบ้าน — `POST /bills/scan-batch`

← [กลับหน้าหลัก](../README.md)

อัปรูปมิเตอร์ทีเดียวได้สูงสุด **30 ใบ** ระบบ OCR ทีละใบแล้วเดาว่าใบไหนเป็นของบ้านหลังไหน

> **ไม่เขียนอะไรลงฐานข้อมูลเลย** — คืนแค่ข้อเสนอพร้อมเหตุผล เมื่อคนตรวจกดยืนยันแล้วหน้าเว็บต้องยิง `POST /bills/scan` ทีละหลัง เพราะ[ด่านกันข้อมูลผิด](billing-rules.md#ด่านกันข้อมูลผิดตอนออกบิล)ทั้งหมดอยู่ที่นั่น

## ทำไมจับคู่ด้วย "เลขมิเตอร์" ไม่ใช่ GPS

เลขมิเตอร์เป็นยอดสะสมตั้งแต่วันติดตั้ง ไม่ได้รีเซ็ตทุกเดือน แต่ละบ้านจึงมีเลขที่ห่างกันมากตามอายุการใช้งาน (บ้านหนึ่ง 1,250 อีกบ้าน 3,891) เลขที่อ่านได้จากรูปจึงชี้กลับไปหาบ้านต้นทางได้เองด้วยเงื่อนไขสองข้อ:

1. **ห้ามติดลบ** — มิเตอร์เดินหน้าอย่างเดียว เลขใหม่ต้อง ≥ เลขตั้งต้นของบ้านนั้น (บ้านที่ทำให้ติดลบถูกตัดทิ้ง)
2. **หน่วยที่ใช้ต้องสมเหตุสมผล** — เทียบกับหน่วยที่บ้านหลังนั้นใช้ตามปกติ ยิ่งใกล้ยิ่งได้คะแนนสูง

เกณฑ์ตัดใช้ค่าเดียวกับ `assertUsageLooksSane()` ของ `BillsService` เป๊ะ ๆ (`USAGE_HARD_CAP` / `USAGE_SPIKE_RATIO` / `USAGE_SPIKE_FLOOR` เป็น static บน `BillsService`) ไม่งั้นหน้านี้จะเสนอบ้านที่พอกดยืนยันจริงแล้วโดนตีกลับเป็น 409

**"หน่วยที่ใช้ตามปกติ" มาจาก `BillsService.usageBaseline()`** = median ของ 6 เดือนล่าสุด ([ทำไมไม่ใช้ค่าเฉลี่ย](billing-rules.md#ด่านกันข้อมูลผิดตอนออกบิล)) — service นี้ **ไม่คำนวณเอง** แต่รับค่า `typical_usage` ที่ `previousUnitsForMembers()` คิดมาให้แล้ว เพื่อการันตีว่าเป็นสูตรเดียวกันจริง

> `Candidate.average_usage` ยังคืนมาเหมือนเดิมแต่เป็น **alias ของ `typical_usage`** (deprecated) — หน้าเว็บรุ่นเก่าจึงไม่พัง แต่ของใหม่ให้ใช้ `typical_usage`

GPS ทำแบบนี้ไม่ได้ เพราะมิเตอร์ห่างกัน 4–20 เมตร (ทาวน์โฮม 4–8, บ้านเดี่ยว 5–20) ขณะที่ GPS มือถือคลาดเคลื่อน 10–30 เมตรเป็นปกติ — รัศมีที่กว้างพอจะไม่ปฏิเสธคนถ่ายถูกบ้าน ย่อมครอบบ้านข้างเคียงไปด้วยเสมอ

## คำเตือนที่ติดมากับแต่ละใบ (`warnings`)

ไม่บล็อกอะไรทั้งสิ้น — บอกล่วงหน้าเพื่อให้คนตัดสินใจตั้งแต่ยังเห็นรูปทั้งชุดอยู่ ด่านที่บล็อกจริงอยู่ที่ `POST /bills/scan`

| เตือนเมื่อ | ด่านจริงที่ปลายทาง |
| --- | --- |
| `confidence` < 0.85 (หลักที่อ่อนที่สุด) | 409 `confirm_low_confidence` |
| `captured_at` ตรงกับการจดที่บันทึกไว้แล้ว | **บล็อกตาย** ไม่มีปุ่มยืนยัน |
| จำนวนหลักต่างจากที่บ้านนี้เคยอ่านได้ | 409 `confirm_digit_change` |
| จุดที่ถ่ายห่างจากบ้านที่เสนอเกินรัศมี | (เตือนอย่างเดียว) |
| วันในรูปไม่ใช่เดือนที่กำลังออกบิล | 409 `confirm_stale_photo` ถ้าห่างเกิน 30 วัน |
| บ้านที่เสนอออกบิลเดือนนี้ไปแล้ว | 409 `replace` |

## ระดับความมั่นใจที่คืนมา

| ค่า         | แปลว่า                                                                |
| ----------- | --------------------------------------------------------------------- |
| `high`      | อันดับ 1 นำอันดับ 2 เกิน 2 เท่า และคะแนน ≥ 0.4 — หน่วยใกล้ค่าเฉลี่ยมาก |
| `medium`    | นำชัดแต่คะแนนไม่สูง หรือบ้านใหม่ที่ยังไม่มีประวัติให้เทียบ             |
| `ambiguous` | เข้าได้หลายบ้านพอ ๆ กัน — `suggestion` เป็น `null` ให้คนเลือกเอง       |
| `none`      | อ่านเลขไม่ได้ หรือไม่เข้ากับบ้านหลังไหนเลย                             |

ทุกใบคืน `reason` เป็นภาษาไทยที่อธิบายว่าทำไมถึงตัดสินแบบนั้น พร้อม `candidates` 5 อันดับแรกให้ทำ dropdown

vision service ล่มไม่ทำให้ทั้งชุด 30 ใบพัง — ใบที่อ่านไม่ได้ตกเป็น `none` แล้วเดินหน้าใบถัดไปต่อ

## ตรวจข้ามใบ: หลายรูปชี้บ้านเดียวกัน

การให้คะแนนมองทีละใบ จึงไม่รู้ว่าใบอื่นเสนอบ้านอะไรไปแล้ว — รูปหลายใบที่เลขมิเตอร์ใกล้กันจะถูกเสนอให้บ้านหลังเดียวกันทั้งหมดอย่างมั่นใจ (`high` ทุกใบ) แล้วไปแตกตอนกดยืนยันทีละใบ: ใบแรกออกบิลผ่าน ที่เหลือโดน 409 บิลซ้ำ และถ้าเผลอกด "จดทับ" ไปเรื่อย ๆ จะเหลือบิลใบเดียว ส่วนบ้านที่เหลือไม่มีบิล

`flagDuplicateSuggestions()` จึงตรวจอีกรอบหลังอ่านครบทุกใบ — ถ้ามี ≥ 2 ใบชี้บ้านเดียวกัน **ลดทุกใบในกลุ่มเป็น `ambiguous`** พร้อมบอกว่าใบไหนชนกับใบไหน:

```json
{
  "index": 0,
  "confidence": "ambiguous",
  "suggestion": null,
  "conflicts_with": [1, 2],
  "reason": "รูปที่ 1, 2, 3 ถูกเสนอให้บ้าน 12/3 เหมือนกันทั้งหมด แต่ 1 บ้านมีบิลได้เดือนละใบเดียว ..."
}
```

`candidates` ยังอยู่ครบให้คนเลือกเอง และ `summary.conflicts` บอกจำนวนใบที่ถูกลดชั้นด้วยเหตุนี้

**ทำไมลดทุกใบ ไม่เก็บใบที่คะแนนดีที่สุดไว้** — เพราะไม่มีข้อมูลพอจะรู้ว่าใบไหนถูก คะแนนที่สูงกว่าเล็กน้อยไม่ได้แปลว่าใบนั้นเป็นของบ้านหลังนี้จริง อาจเป็นรูปเดียวกันถ่ายซ้ำ หรือ OCR อ่านผิดทั้งกอง การเลือกใบที่คะแนนสูงสุดไว้คือการเดาที่ดูน่าเชื่อถือ ซึ่งอันตรายกว่าการบอกว่าไม่รู้ (แนวเดียวกับ `gpsTiebreak` ที่ยอมคืน `null` เมื่อข้อมูลไม่พอ)

## บ้านที่ออกบิลเดือนนี้ไปแล้ว

คะแนนถูกคูณด้วย `ALREADY_BILLED_PENALTY = 0.3` — ไม่ตัดทิ้ง เพราะจดผิดแล้วมาแก้เป็นเรื่องปกติ แต่ต้องไม่ชนะบ้านที่ยังไม่มีบิลซึ่งเข้าเค้าพอ ๆ กัน ไม่งั้นรูปของบ้านที่ยังไม่ได้ออกบิลจะถูกเสนอให้ไปทับใบของบ้านข้าง ๆ

ถ้าสุดท้ายยังถูกเสนออยู่ จะมีคำเตือนติดไปด้วยว่าการยืนยันคือการจดทับของเดิม

## บทบาทของ GPS: ใช้ตัดสินเสมอกันเท่านั้น

พิกัดถูกอ่านจาก EXIF ของไฟล์รูป (`PhotoMetadataService`) และเอามาใช้ **แค่ 2 อย่าง**:

- **ตัดสินตอนเสมอ** (`gpsTiebreak`) — ยอมตัดสินเฉพาะตอนที่ผลต่างชัดจริง คือหลังหนึ่งอยู่ในระยะ ≤ `GPS_NEAR_M` (50 ม.) ขณะที่อีกหลังไกลเกินรัศมี "น่าสงสัย" ของหมู่บ้านนั้น ถ้าทั้งคู่ใกล้พอ ๆ กัน (ซึ่งเป็นเรื่องปกติ) ต้องคืน `null` ให้คนเลือกเอง และผลลัพธ์ได้แค่ `medium` ไม่มีทางเป็น `high`
- **เตือน** — จุดที่ถ่ายห่างจากบ้านที่เสนอเกินรัศมีนั้น หรือวันในรูปไม่ใช่เดือนที่กำลังออกบิล จะขึ้นใน `warnings` แต่ไม่บล็อก (นาฬิกากล้องตั้งผิดเจอบ่อย และ EXIF ไม่มี timezone ติดมาด้วย)

### รัศมี "ไกลจนน่าสงสัย" คิดจากความหนาแน่นของหมู่บ้าน

`farThresholdFor()` = `villages.meter_pitch_m × 10` แล้ว clamp ไว้ที่ **80–150 ม.** (`meter_pitch_m` = ระยะเดินเฉลี่ยต่อ 1 มิเตอร์ ยังไม่กรอก = ใช้ค่ากลาง 15 ม. → 150 ม. เท่าพฤติกรรมเดิม)

ที่ต้องผูกกับหมู่บ้าน เพราะรัศมี R ครอบบ้านราว `2 × (2R / pitch)` หลัง — ค่าคงที่ 150 ม. จึงให้ผลคนละเรื่องในหมู่บ้าน 150 หลังคาเรือน:

| ประเภทหมู่บ้าน | `meter_pitch_m` | รัศมี | บ้านที่ติดอยู่ในรัศมี |
| --- | --- | --- | --- |
| ชนบท / บ้านเดี่ยว | 15 | 150 ม. | ~40 หลัง (27%) |
| ชุมชนทั่วไป | 10 | 100 ม. | ~40 หลัง (27%) |
| ทาวน์โฮมหน้าแคบ | 6 | 80 ม. | ~53 หลัง (36%) |

ถ้าไม่หด ทาวน์โฮมที่ pitch 6 ม. จะโดนรัศมี 150 ม. ครอบ ~100 หลัง = 67% ของหมู่บ้าน กลายเป็นด่านที่แทบไม่ตัดอะไรทิ้ง

ส่วน `GPS_NEAR_M` **ไม่หดตามหมู่บ้าน** เพราะเป็นคำถามเรื่องความแม่นของ GPS ไม่ใช่ความหนาแน่น — จุดอ้างอิงตอนลงทะเบียนคลาดได้ 20 ม. บวกตอนถ่ายอีก ~30 ม. รวมเป็น √(20² + 30²) ≈ 36 ม. (`GPS_COMBINED_ERROR_M`) ถ้าหดตามหมู่บ้านหนาแน่นจะกลายเป็นปฏิเสธคนที่ถ่ายถูกบ้านแทน

### รัศมี "ใกล้" หดตาม **บ้าน** แทน — `spread_m` (MAD)

`learnedMeterLocations()` คืน `spread_m` มาด้วย = มัธยฐานของระยะจากจุดกลางถึงแต่ละครั้งที่เคยไปจดบ้านหลังนั้น (ต้องมี ≥ 3 ครั้ง ไม่งั้นเป็น `null`)

ความแม่นจริงต่างกันมากตามหน้างาน — มิเตอร์กลางทุ่งโล่งจับดาวเทียมได้ 8 ดวง กระจายไม่ถึง 5 ม. ส่วนมิเตอร์ใต้ชายคาติดกำแพงกระจายได้ถึง 40 ม. รัศมีเดียวกันทั้งระบบจึงหลวมเกินไปสำหรับบ้านแรกและคับเกินไปสำหรับบ้านหลัง

`nearLimitFor(candidate)` = `clamp(2 × spread_m, 36, 50)` — ใช้ MAD ไม่ใช่ SD ด้วยเหตุผลเดียวกับจุดกลาง: ครั้งที่ GPS ยังไม่ fix ให้พิกัดผิดเป็นกิโล ซึ่งจะทำให้ SD ระเบิด

### `gpsTiebreak` ต้องผ่านครบ 3 ข้อ

| ข้อ | เงื่อนไข | ตอบคำถามอะไร |
| --- | --- | --- |
| 1 | `d₁ ≤ nearLimit(top)` | ใกล้พอจะเป็นบ้านหลังนี้จริงไหม |
| 2 | `d₂ > farM` | อีกหลังไกลเกินความหนาแน่นของหมู่บ้านนี้ไหม |
| 3 | `d₂ - d₁ > 36 ม.` | ช่องว่างกว้างกว่าความคลาดเคลื่อนของการวัดเองไหม |

**ข้อ 3 สำคัญที่สุด** — ถ้าไม่มี ระยะ 45 ม. กับ 52 ม. จะถูกตีความว่า "หลังแรกใกล้กว่า" ทั้งที่ต่างกัน 7 ม. ซึ่งน้อยกว่าความคลาดเคลื่อนของการวัดครั้งเดียวหลายเท่า วัดใหม่อีกรอบอันดับอาจสลับกันเลย

**พิกัดอ้างอิงของบ้านใช้ 2 แหล่ง เรียงตามความน่าเชื่อถือ:**

1. **พิกัดที่เรียนรู้จากการจดจริง** (`learnedMeterLocations`) — มัธยฐานของพิกัดทุกครั้งที่เคยไปยืนจดบ้านหลังนั้น ต้องมีอย่างน้อย 2 ครั้งถึงจะเชื่อ
   ใช้ **มัธยฐาน ไม่ใช่ค่าเฉลี่ย** เพราะครั้งที่ GPS ยังไม่ fix จะให้พิกัดผิดไปเป็นกิโล ค่าเฉลี่ยจะถูกลากไปทั้งชุดจากค่าเดียว
2. **`members.latitude/longitude` ในทะเบียน** — ใช้เมื่อยังมีประวัติไม่พอ มักมาจากการจิ้มหมุดบนแผนที่ (กลางหลังคา) ขณะที่มิเตอร์อยู่ริมรั้ว จึงมีระยะเหลื่อมติดอยู่ 10–15 ม. ทุกครั้ง พอ ๆ กับระยะห่างระหว่างบ้าน

ข้อ 1 ดีกว่าเพราะทั้งจุดอ้างอิงและจุดที่วัดมาจากเซนเซอร์เดียวกัน ยืนที่เดียวกัน ความคลาดเคลื่อนแบบคงที่จึงหักล้างกันเอง เหลือแต่ error สุ่มที่เฉลี่ยทิ้งได้

## มิเตอร์ที่ติดกันเป็นกลุ่ม — GPS ถูกปิดทั้งหมด

มิเตอร์ทาวน์โฮม/ห้องเช่าเรียงติดกันบนกำแพงเดียวกัน ห่างกันราว **30 ซม.** ขณะที่ GPS มือถือคลาดเคลื่อน 3–5 ม. ในที่โล่ง และ 10–30 ม. ใต้ชายคา — ความคลาดเคลื่อนกว้างกว่าระยะจริงเป็นสิบเท่า **ไม่มีค่ารัศมีไหนแก้ได้** เพราะเป็นเพดานของเครื่องมือ ไม่ใช่เรื่องการตั้งค่า

ทางแก้คือเลิกถามพิกัดสำหรับกลุ่มนี้ แล้วใช้ตำแหน่งตายตัวที่กรอกไว้ล่วงหน้าใน `members` แทน (ดู `db/migrate-meter-clusters.sql`):

| คอลัมน์ | ความหมาย |
| --- | --- |
| `cluster_group_id` | ป้ายชื่อกลุ่มมิเตอร์ที่ติดกัน (NULL = บ้านเดี่ยว ทุกอย่างทำงานเหมือนเดิม) |
| `sequence_index` | ตำแหน่งซ้าย→ขวาเมื่อหันหน้าเข้าหากำแพง (1 = ซ้ายสุด) ห้ามซ้ำในกลุ่มเดียวกัน |

**สิ่งที่ถูกปิดเมื่อสองบ้านอยู่กลุ่มเดียวกัน**

| ด่าน | ที่อยู่ | ทำไมต้องปิด |
| --- | --- | --- |
| `gpsTiebreak` | `ScanBatchService.judge` | ระยะที่ต่างกันคือ 30 ซม. ส่วนความคลาดเคลื่อนคือหลายเมตร ผลที่ได้เป็นเสียงรบกวนล้วน ๆ → คืน `ambiguous` พร้อมข้อความให้ไล่จดตามลำดับแทน |
| คำเตือน "ถ่ายรัวที่จุดเดิม" | `ScanBatchService.flagBurstPhotos` | เดินไปถ่ายตัวถัดไปจริง ๆ ก็ขยับแค่ 30 ซม. ในไม่กี่วินาที = เข้าเกณฑ์ทุกครั้งที่ทำถูก |
| ด่าน `BURST_PHOTO` | `BillsService.assertPhotoNotReused` | เหตุผลเดียวกัน แต่ตัวนี้บล็อกจริงตอนกดออกบิล |
| ด่าน `DUPLICATE_LOCATION` | `BillsService.assertPhotoNotReused` | GPS ให้ค่าเดิมเป๊ะสองครั้งได้จริงที่ระยะ 30 ซม. (ต่ำกว่าที่เครื่องแยกออกหลายเท่า) — ยังบล็อกอยู่ถ้าพิกัดไปซ้ำกับบ้าน **นอกกลุ่ม** |
| การเดาบ้านจากพิกัด | หน้าเว็บ (`matchByCoords`) | "หลังที่ใกล้ที่สุด" ในกลุ่มคือผลของเสียงรบกวน เติมให้เท่ากับให้คนเซ็นรับรองการเดา |

**สิ่งที่มาแทน**

- **หลังบ้าน — ตัวเลข:** `assertClusterReadingFits()` เทียบ `current_unit` กับ `previous_unit` ของทุกหลังในกลุ่ม ถ้าเลขต่ำกว่าเลขตั้งต้นของหลังที่เลือกแต่เข้ากับเพื่อนบ้านในกลุ่มพอดีหลังเดียว จะตีกลับด้วยรหัส `CLUSTER_SEQUENCE_MISMATCH` พร้อมบอกบ้านและตำแหน่งที่น่าจะถูก (ไม่มีปุ่มยืนยัน — ทางแก้คือเลือกบ้านให้ถูก ไม่ใช่ปล่อยผ่าน)
- **หน้าเว็บ — ลำดับ:** หน้าสแกนล็อกให้จดไล่จากซ้ายไปขวา บ้านที่ยังไม่ถึงคิวกดไม่ได้ พร้อมป้าย "ตำแหน่ง: ซ้ายสุด / ตรงกลาง / ขวาสุด" ทุกจุดที่แสดงบ้านเลขที่ (ข้อความต้องตรงกับ `BillsService.positionLabel()` คำต่อคำ)

`candidates[]` จึงมี `cluster_group_id` กับ `sequence_index` ติดมาด้วยทุกใบ เพื่อให้หน้าเว็บล็อกลำดับได้โดยไม่ต้องยิงถามซ้ำ

## EXIF หายง่ายมาก

ในระบบนี้มีจุดที่ลบ EXIF ทิ้งอยู่ 2 จุด:

1. หน้าเว็บย่อ/ครอปรูปด้วย canvas ก่อนส่ง — canvas วาดพิกเซลใหม่ metadata ไม่ติดไปด้วย
2. `MeterPhotoService.save()` ผ่าน `sharp().rotate().jpeg()` — sharp ทิ้ง metadata เป็นค่าเริ่มต้น

`PhotoMetadataService.read()` จึงต้องถูกเรียกกับ buffer ที่รับมาจาก multipart **ก่อน** ส่งต่อให้ใครทั้งสิ้น (รวมถึงก่อนยิงไป vision service เผื่อฝั่งนั้นล่ม) ถ้าได้ `has_exif: false` แปลว่ารูปผ่านการประมวลผลมาแล้ว ไม่ใช่ว่าไม่มีข้อมูลตั้งแต่ต้น

> **ทางที่ดีกว่าคืออย่าพึ่ง EXIF** — `POST /bills/scan` รับ `latitude` / `longitude` / `gps_accuracy_m` / `captured_at` เป็นฟิลด์ตรง ๆ ใน body ให้หน้าเว็บส่งค่าจาก `navigator.geolocation.getCurrentPosition()` ตอนกดชัตเตอร์แทน ได้ `accuracy` แถมมาด้วยซึ่ง EXIF ไม่มีให้ และไม่ต้องพึ่งว่าผู้ใช้เปิด geotag ไว้หรือเปล่า (ส่วนใหญ่ปิด)
