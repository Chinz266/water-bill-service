# จับคู่รูปกับบ้าน — `POST /bills/scan-batch`

← [กลับหน้าหลัก](../README.md)

อัปรูปมิเตอร์ทีเดียวได้สูงสุด **30 ใบ** ระบบ OCR ทีละใบแล้วเดาว่าใบไหนเป็นของบ้านหลังไหน

> **ไม่เขียนอะไรลงฐานข้อมูลเลย** — คืนแค่ข้อเสนอพร้อมเหตุผล เมื่อคนตรวจกดยืนยันแล้วหน้าเว็บต้องยิง `POST /bills/scan` ทีละหลัง เพราะ[ด่านกันข้อมูลผิด](billing-rules.md#ด่านกันข้อมูลผิดตอนออกบิล)ทั้งหมดอยู่ที่นั่น

## ทำไมจับคู่ด้วย "เลขมิเตอร์" ไม่ใช่ GPS

เลขมิเตอร์เป็นยอดสะสมตั้งแต่วันติดตั้ง ไม่ได้รีเซ็ตทุกเดือน แต่ละบ้านจึงมีเลขที่ห่างกันมากตามอายุการใช้งาน (บ้านหนึ่ง 1,250 อีกบ้าน 3,891) เลขที่อ่านได้จากรูปจึงชี้กลับไปหาบ้านต้นทางได้เองด้วยเงื่อนไขสองข้อ:

1. **ห้ามติดลบ** — มิเตอร์เดินหน้าอย่างเดียว เลขใหม่ต้อง ≥ เลขตั้งต้นของบ้านนั้น (บ้านที่ทำให้ติดลบถูกตัดทิ้ง)
2. **หน่วยที่ใช้ต้องสมเหตุสมผล** — เทียบกับที่บ้านหลังนั้นเคยใช้จริง ยิ่งใกล้ค่าเฉลี่ยยิ่งได้คะแนนสูง

เกณฑ์ตัดใช้ค่าเดียวกับ `assertUsageLooksSane()` ของ `BillsService` เป๊ะ ๆ (`USAGE_HARD_CAP` / `USAGE_SPIKE_RATIO` / `USAGE_SPIKE_FLOOR` เป็น static บน `BillsService`) ไม่งั้นหน้านี้จะเสนอบ้านที่พอกดยืนยันจริงแล้วโดนตีกลับเป็น 409

GPS ทำแบบนี้ไม่ได้ เพราะบ้านในหมู่บ้านห่างกัน 8–20 เมตร ขณะที่ GPS มือถือคลาดเคลื่อน 10–30 เมตรเป็นปกติ — รัศมีที่กว้างพอจะไม่ปฏิเสธคนถ่ายถูกบ้าน ย่อมครอบบ้านข้างเคียงไปด้วยเสมอ

## ระดับความมั่นใจที่คืนมา

| ค่า         | แปลว่า                                                                |
| ----------- | --------------------------------------------------------------------- |
| `high`      | อันดับ 1 นำอันดับ 2 เกิน 2 เท่า และคะแนน ≥ 0.4 — หน่วยใกล้ค่าเฉลี่ยมาก |
| `medium`    | นำชัดแต่คะแนนไม่สูง หรือบ้านใหม่ที่ยังไม่มีประวัติให้เทียบ             |
| `ambiguous` | เข้าได้หลายบ้านพอ ๆ กัน — `suggestion` เป็น `null` ให้คนเลือกเอง       |
| `none`      | อ่านเลขไม่ได้ หรือไม่เข้ากับบ้านหลังไหนเลย                             |

ทุกใบคืน `reason` เป็นภาษาไทยที่อธิบายว่าทำไมถึงตัดสินแบบนั้น พร้อม `candidates` 5 อันดับแรกให้ทำ dropdown

vision service ล่มไม่ทำให้ทั้งชุด 30 ใบพัง — ใบที่อ่านไม่ได้ตกเป็น `none` แล้วเดินหน้าใบถัดไปต่อ

## ตรวจข้ามใบ: หลายรูปชี้บ้านเดียวกัน

การให้คะแนนมองทีละใบ จึงไม่รู้ว่าใบอื่นเสนอบ้านอะไรไปแล้ว — รูปหลายใบที่เลขมิเตอร์ใกล้กันจะถูกเสนอให้บ้านหลังเดียวกันทั้งหมดอย่างมั่นใจ (`high` ทุกใบ) แล้วไปแตกตอนกดยืนยันทีละใบ: ใบแรกออกบิลผ่าน ที่เหลือโดน 409 บิลซ้ำ และถ้าเผลอกด "จดทับ" ไปเรื่อย ๆ จะเหลือบิลใบเดียว ส่วนบ้านที่เหลือไม่มีบิล

`flagDuplicateSuggestions()` จึงตรวจอีกรอบหลังอ่านครบทุกใบ — ถ้ามี ≥ 2 ใบชี้บ้านเดียวกัน **ลดทุกใบในกลุ่มเป็น `ambiguous`** พร้อมบอกว่าใบไหนชนกับใบไหน:

```json
{
  "index": 0,
  "confidence": "ambiguous",
  "suggestion": null,
  "conflicts_with": [1, 2],
  "reason": "รูปที่ 1, 2, 3 ถูกเสนอให้บ้าน 12/3 เหมือนกันทั้งหมด แต่ 1 บ้านมีบิลได้เดือนละใบเดียว ..."
}
```

`candidates` ยังอยู่ครบให้คนเลือกเอง และ `summary.conflicts` บอกจำนวนใบที่ถูกลดชั้นด้วยเหตุนี้

**ทำไมลดทุกใบ ไม่เก็บใบที่คะแนนดีที่สุดไว้** — เพราะไม่มีข้อมูลพอจะรู้ว่าใบไหนถูก คะแนนที่สูงกว่าเล็กน้อยไม่ได้แปลว่าใบนั้นเป็นของบ้านหลังนี้จริง อาจเป็นรูปเดียวกันถ่ายซ้ำ หรือ OCR อ่านผิดทั้งกอง การเลือกใบที่คะแนนสูงสุดไว้คือการเดาที่ดูน่าเชื่อถือ ซึ่งอันตรายกว่าการบอกว่าไม่รู้ (แนวเดียวกับ `gpsTiebreak` ที่ยอมคืน `null` เมื่อข้อมูลไม่พอ)

## บ้านที่ออกบิลเดือนนี้ไปแล้ว

คะแนนถูกคูณด้วย `ALREADY_BILLED_PENALTY = 0.3` — ไม่ตัดทิ้ง เพราะจดผิดแล้วมาแก้เป็นเรื่องปกติ แต่ต้องไม่ชนะบ้านที่ยังไม่มีบิลซึ่งเข้าเค้าพอ ๆ กัน ไม่งั้นรูปของบ้านที่ยังไม่ได้ออกบิลจะถูกเสนอให้ไปทับใบของบ้านข้าง ๆ

ถ้าสุดท้ายยังถูกเสนออยู่ จะมีคำเตือนติดไปด้วยว่าการยืนยันคือการจดทับของเดิม

## บทบาทของ GPS: ใช้ตัดสินเสมอกันเท่านั้น

พิกัดถูกอ่านจาก EXIF ของไฟล์รูป (`PhotoMetadataService`) และเอามาใช้ **แค่ 2 อย่าง**:

- **ตัดสินตอนเสมอ** (`gpsTiebreak`) — ยอมตัดสินเฉพาะตอนที่ผลต่างชัดจริง คือหลังหนึ่งอยู่ในระยะ ≤ 50 ม. ขณะที่อีกหลังไกลเกิน 150 ม. ถ้าทั้งคู่ใกล้พอ ๆ กัน (ซึ่งเป็นเรื่องปกติ) ต้องคืน `null` ให้คนเลือกเอง และผลลัพธ์ได้แค่ `medium` ไม่มีทางเป็น `high`
- **เตือน** — จุดที่ถ่ายห่างจากบ้านที่เสนอเกิน 150 ม. หรือวันในรูปไม่ใช่เดือนที่กำลังออกบิล จะขึ้นใน `warnings` แต่ไม่บล็อก (นาฬิกากล้องตั้งผิดเจอบ่อย และ EXIF ไม่มี timezone ติดมาด้วย)

**พิกัดอ้างอิงของบ้านใช้ 2 แหล่ง เรียงตามความน่าเชื่อถือ:**

1. **พิกัดที่เรียนรู้จากการจดจริง** (`learnedMeterLocations`) — มัธยฐานของพิกัดทุกครั้งที่เคยไปยืนจดบ้านหลังนั้น ต้องมีอย่างน้อย 2 ครั้งถึงจะเชื่อ
   ใช้ **มัธยฐาน ไม่ใช่ค่าเฉลี่ย** เพราะครั้งที่ GPS ยังไม่ fix จะให้พิกัดผิดไปเป็นกิโล ค่าเฉลี่ยจะถูกลากไปทั้งชุดจากค่าเดียว
2. **`members.latitude/longitude` ในทะเบียน** — ใช้เมื่อยังมีประวัติไม่พอ มักมาจากการจิ้มหมุดบนแผนที่ (กลางหลังคา) ขณะที่มิเตอร์อยู่ริมรั้ว จึงมีระยะเหลื่อมติดอยู่ 10–15 ม. ทุกครั้ง พอ ๆ กับระยะห่างระหว่างบ้าน

ข้อ 1 ดีกว่าเพราะทั้งจุดอ้างอิงและจุดที่วัดมาจากเซนเซอร์เดียวกัน ยืนที่เดียวกัน ความคลาดเคลื่อนแบบคงที่จึงหักล้างกันเอง เหลือแต่ error สุ่มที่เฉลี่ยทิ้งได้

## EXIF หายง่ายมาก

ในระบบนี้มีจุดที่ลบ EXIF ทิ้งอยู่ 2 จุด:

1. หน้าเว็บย่อ/ครอปรูปด้วย canvas ก่อนส่ง — canvas วาดพิกเซลใหม่ metadata ไม่ติดไปด้วย
2. `MeterPhotoService.save()` ผ่าน `sharp().rotate().jpeg()` — sharp ทิ้ง metadata เป็นค่าเริ่มต้น

`PhotoMetadataService.read()` จึงต้องถูกเรียกกับ buffer ที่รับมาจาก multipart **ก่อน** ส่งต่อให้ใครทั้งสิ้น (รวมถึงก่อนยิงไป vision service เผื่อฝั่งนั้นล่ม) ถ้าได้ `has_exif: false` แปลว่ารูปผ่านการประมวลผลมาแล้ว ไม่ใช่ว่าไม่มีข้อมูลตั้งแต่ต้น

> **ทางที่ดีกว่าคืออย่าพึ่ง EXIF** — `POST /bills/scan` รับ `latitude` / `longitude` / `gps_accuracy_m` / `captured_at` เป็นฟิลด์ตรง ๆ ใน body ให้หน้าเว็บส่งค่าจาก `navigator.geolocation.getCurrentPosition()` ตอนกดชัตเตอร์แทน ได้ `accuracy` แถมมาด้วยซึ่ง EXIF ไม่มีให้ และไม่ต้องพึ่งว่าผู้ใช้เปิด geotag ไว้หรือเปล่า (ส่วนใหญ่ปิด)
