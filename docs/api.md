### แก้เลขมิเตอร์ของบิลที่ออกไปแล้ว — `PATCH /bills/:id/reading`

`multipart/form-data`: `current_unit`, `reason` (บังคับ), `photo` (ไฟล์, ไม่บังคับ), `confirm_high_usage`, `confirm_meter_reset`
คืน `{ usage_unit, total_amount, grand_total }`

| สิทธิ์ (`admin_role` ใน token) | แก้ได้เมื่อ                                       |
| ------------------------------ | ------------------------------------------------- |
| `owner`                        | ตลอด ยกเว้นบิลที่ `Paid`                          |
| `staff`                        | บิลที่ **จดวันนี้** หรือบิลที่ยังเป็น `Pending`    |

- บิลที่ `Paid` แก้ไม่ได้แม้เป็น `owner` → ต้อง `PATCH /bills/:id/status` กลับเป็น `Pending` ก่อน (ตอบ 409 `code: BILL_PAID`)
- ติดด่านตอบ **400** พร้อม `{ message, code: 'high_usage' | 'meter_reset' }` — หน้าเว็บอ่าน `code` เพื่อเปิดปุ่มยืนยัน แล้วยิงซ้ำพร้อม `confirm_*` **เฉพาะรอบนั้น** (ห้ามติ๊กล่วงหน้า) error ที่ไม่มี `code` = error ธรรมดา ห้ามขึ้นปุ่มให้กดข้าม
- รูปที่แนบมาถูกครอปจากหน้าเว็บแล้วจึงไม่มี EXIF — ระบบ **ไม่เอาไปอัปเดตพิกัด/เวลาถ่าย** ของการจดครั้งนั้น
- แก้สำเร็จให้โหลดประวัติบิลใหม่ทั้งชุด: ยอดค้างที่ใบอื่นทบใบนี้ไว้ (`arrears_amount` / `grand_total`) ถูกคิดใหม่ตามไปด้วย
- ทุกครั้งที่แก้จะมีแถวลง `meter_reading_logs` (เลขเดิม/ใหม่ ยอดเดิม/ใหม่ เหตุผล ใครแก้) ดูผ่าน `GET /audit/reading-logs?bills_id=`

### คิวรอการตรวจสอบ — `/readings/unassigned`

คิวเดียวรับรูปที่ยังออกบิลไม่ได้ **สองแบบ** แยกกันด้วย `members_id`:

| แบบ | `members_id` | `blocked_code` | คนตรวจต้องทำอะไร |
| --- | --- | --- | --- |
| ไม่รู้ว่าบ้านไหน (กำพร้า) | `null` | `null` | เลือกบ้านจาก `candidates` |
| รู้บ้านแล้ว แต่ด่านตีกลับ | บ้านที่คนหน้างานเลือก | รหัสด่าน เช่น `HIGH_USAGE` | เปิดรูปเทียบ แล้วติ๊ก `confirm_*` ที่ตรงกับรหัสนั้น |

แบบที่สองคือ **"รอการตรวจสอบ"** — ด่านตีกลับด้วย 409 แล้วคนหน้างานเลือกไม่กดยืนยันเอง จึงฝากไว้ให้คนที่มีเวลาเปิดรูปเทียบเป็นคนอนุมัติแทน (ดู `db/migrate-review-queue.sql` ว่าทำไมใช้ตารางเดียวกัน)

- `GET /readings/unassigned/:id?month=&year=` คืน `suggested` เพิ่มมาด้วยเมื่อมี `members_id` — บ้าน + `previous_unit` + `usage_unit` + ตำแหน่งในกลุ่มมิเตอร์ **ไม่ได้หยิบจาก `candidates`** เพราะแถวที่ถูกด่านตีกลับคือแถวที่เลข "ไม่เข้า" พอดี บ้านที่ถูกต้องจึงมักไม่ติดอันดับ ซึ่งเป็นเรื่องปกติของเคสนี้
- `POST /readings/unassigned/:id/assign` ไม่ส่ง `members_id` มา = ยืนตามบ้านที่คนหน้างานเลือกไว้ ส่งมา = เปลี่ยนบ้าน (ทำได้เสมอ — เหตุผลหนึ่งที่รูปมาอยู่ในคิวคือ "อาจจดสลับบ้าน")
- อนุมัติแล้ววิ่งผ่าน `POST /bills/scan` ตัวเดิมทั้งหมด **ด่านที่เหลือยังทำงานครบ** ไม่ใช่ทางลัดที่ข้ามทุกด่าน

#### `relative` — ทิศทางของจุดที่ถ่าย เทียบกับหมุดที่ลงทะเบียนไว้

ทุก candidate มี `relative` ติดมา: `{ distance_meters, bearing_deg, relative_direction, within_threshold, reliable, from_sequence }` — ทิศเป็นสี่ทาง (`บน`/`ล่าง`/`ซ้าย`/`ขวา`) แบ่งที่ 45° ตามแนวทแยง, `within_threshold` = ระยะ ≤ 0.3 ม., พิกัดซ้ำกันเป๊ะจะถอยไปใช้ `sequence_index` (`from_sequence: true`)

> ⚠️ **`reliable: false` เมื่อระยะ < 3 ม. — ห้ามเอาไปตัดสินว่าเป็นบ้านไหน**
> GPS มือถือคลาดเคลื่อน 3–5 ม. ในที่โล่ง และ 10–30 ม. ใต้ชายคา ทิศที่คำนวณจากระยะ 30 ซม. จึงเป็นเสียงรบกวน ไม่ใช่ตำแหน่งจริง — ถ่ายมิเตอร์ตัวเดิมสองครั้งจะได้ทิศคนละทาง
> ฟิลด์นี้มีไว้ **แสดงประกอบให้คนดู** เท่านั้น ตัวที่ตอบ "ตัวไหนของบ้านไหน" ได้จริงคือ `sequence_index` (ดู `db/migrate-meter-clusters.sql`)

#### `chain` — มิเตอร์ตัวเดียวกันที่ถ่ายคนละวัน

ทุกแถวที่คืนจาก `GET /readings/unassigned` (และ `/:id`) มี `chain` ติดมาด้วย = ใบก่อนหน้าของ**มิเตอร์ตัวเดียวกัน** (`null` = เชื่อมไม่ได้)

```json
"chain": {
  "id": 9, "captured_at": "2026-08-15T09:00:00", "meter_unit": 57,
  "usage_unit": 33, "days_apart": 3, "distance_m": 4,
  "status": "Assigned", "members_id": 7, "house_no": "206/2", "cluster_group_id": null
}
```

เกิดจากเคสที่คนเดินจดถ่ายมิเตอร์ตัวเดิมซ้ำคนละวัน (15 ส.ค. ได้ 57, 18 ส.ค. ได้ 90) แล้วทั้งสองใบค้างเป็น "ไม่รู้ว่าบ้านไหน" เหมือนกัน — พอใบแรกถูกจับคู่ ใบหลังก็ตอบได้ทันที (`members_id` / `house_no` ของใบก่อนติดมาให้เลย)

**เกณฑ์ (ต้องผ่านครบ)** — มีเลขมิเตอร์ทั้งคู่ · มีพิกัดทั้งคู่และห่างกัน ≤ `CHAIN_NEAR_M` (45 ม. = √(30²+30²) ของความคลาดเคลื่อนสองครั้ง) · ใบก่อนถ่ายก่อนจริง · เลขไม่ลดลง · จำนวนหลักตรงกันเมื่อรู้ทั้งคู่ · ห่างกัน ≤ 45 วัน. เลือกใบที่**ชิดที่สุด**ก่อนหน้า และถ้ามีสองใบเวลาเท่ากันเป๊ะจะไม่เชื่อมเลย

**ไม่ได้เก็บลงตาราง** — คิดสดทุกครั้งจากพิกัด/เวลา/เลข เพราะ "ใบก่อนหน้า" เปลี่ยนไปตามของที่เข้ามาใหม่และที่ถูกตีทิ้ง คอลัมน์ที่จดไว้จะค้างชี้ของเก่าแล้วต้องมีโค้ดตามล้างทุกเส้นทาง

⚠️ `chain` ตอบว่า **"น่าจะเป็นมิเตอร์ตัวเดียวกัน"** ไม่ได้ตอบว่าเป็นบ้านไหน — มิเตอร์ที่ติดกันบนกำแพงเดียวกันห่างกัน 30 ซม. ซึ่งพิกัดแยกไม่ออก จึงส่ง `cluster_group_id` ของใบก่อนมาด้วยให้หน้าเว็บขึ้นคำเตือน และคนต้องเป็นผู้กดยืนยันเสมอ

## Vision service — `http://localhost:8000`

| Method | Path      | หมายเหตุ                                                 |
| ------ | --------- | -------------------------------------------------------- |
| GET    | `/health` | เช็คสถานะ + ดู class ของโมเดล                            |
| POST   | `/detect` | อัปโหลดรูป (multipart field ชื่อ `file`) → คืนเลขมิเตอร์ |

โมเดลมี 12 class: `0`–`9` คือตัวเลขแต่ละหลัก, `10` = `border_decimal_point`, `11` = `border_water_meter_number`

```json
{
  "success": true,
  "read_unit": "00025",
  "integer_part": "00025",
  "decimal_part": "312",
  "full_reading": "00025312",
  "confidence": 0.91,
  "crop_box": { "x": 0, "y": 0.47, "w": 1, "h": 0.22, "source": "digits" }
}
```

`crop_box` คือกรอบที่โมเดลชี้ว่าแถวตัวเลขอยู่ตรงไหน — **สัดส่วน 0-1 ของภาพ ไม่ใช่พิกเซล** หน้าเว็บเอาไปตั้งเป็นกรอบเริ่มต้นของ `ngx-image-cropper` แล้วคนลากปรับต่อได้ (`source: "digits"` = กรอบของเลขสีดำล้วน ซึ่งเป็นกรอบที่ต้องการจริง ๆ, `"border"` = ทั้งแถบเลขมิเตอร์ ใช้เมื่ออ่านหลักจำนวนเต็มไม่ได้เลย จึงยังไม่ได้ตัดเลขแดงออก), `null` = โมเดลไม่เห็นอะไรให้ชี้ ให้ใช้กรอบกลางภาพตามเดิม

กรอบที่ได้เป็น**แถบแนวนอนเต็มความกว้างภาพ สูงตามสัดส่วน 3:1 วางกลางที่แถวตัวเลข** — งานของมันคือตัดส่วนบน/ล่างที่ไม่เกี่ยวออก ไม่ใช่ซูมเข้าไปที่ตัวเลข ตรงกับกรอบที่คนหน้างานลากเองแล้วยืนยันว่าโมเดลอ่านออก (กรอบที่แนบขอบเลขทำให้รอบสองเหลือแต่ตัวเลขลอย ๆ ไม่มีหน้าปัดให้อ้างอิงว่าแถวเลขอยู่ตรงไหน)

3:1 ต้องตรงกับ ratio ที่หน้า cropper ล็อกไว้ (เลือก 4:1 ได้ แต่ค่าเริ่มต้นคือ 3:1) — กรอบสัดส่วนอื่นจะถูก `ngx-image-cropper` บิดให้เข้า ratio ทันทีที่ตั้ง กรอบที่คนเห็นจึงไม่ใช่กรอบที่ vision service คำนวณไว้

> ⚠️ **`crop_box` เป็นพิกัดของภาพตามที่เก็บในไฟล์ ยังไม่หมุนตาม EXIF Orientation**
> vision service อ่านรูปด้วย PIL ซึ่งไม่หมุนภาพให้ รูปมือถือที่ถ่ายแนวตั้งจะได้กรอบเอียง 90 องศาเทียบกับที่คนเห็นบนจอ
> หน้าเว็บต้องหมุนกรอบตาม EXIF ก่อนใช้เสมอ (`mapBoxThroughExif` ใน `meter-cropper.ts`)

`POST /meter-readings/ocr-upload` คืนผลชุดนี้ต่อให้หน้าเว็บ พร้อม `meter_digits` (จำนวนหลักที่นับจาก `integer_part`) และ `photo_taken` (EXIF) ที่ backend เติมให้ — **หน้าเว็บต้องส่ง `meter_digits` ต่อไปกับ `POST /bills/scan`** ไม่งั้นด่านจำนวนหลักจะไม่ทำงาน

> ⚠️ **backend ใช้ `integer_part` เท่านั้น** — เลขสีดำบนหน้าปัด (ลูกบาศก์เมตร)
> `full_reading` รวมเลขทศนิยม (เข็มแดง) มาด้วย มิเตอร์ที่อ่านได้ 25.312 จะกลายเป็น 25312 ใหญ่เกินจริง 1,000 เท่า
> ตัวเลขนี้ถูกส่งต่อเป็น `current_unit` ตรง ๆ อ่านผิดจึงเท่ากับยอดเงินผิดทันที

Vision service ใช้เวลาโหลดโมเดลตอนสตาร์ท — รอ `/health` ตอบ 200 ก่อนค่อยยิงงานเข้าไป
