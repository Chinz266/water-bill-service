# WaterService — ระบบจัดการค่าน้ำประปาหมู่บ้าน

ระบบอ่านเลขมิเตอร์น้ำจากรูปถ่ายด้วยโมเดล YOLO แล้วคิดบิลค่าน้ำ ประกอบด้วย 4 ส่วนที่ต้องรันพร้อมกัน

```
┌─────────────────────┐
│  Angular  :4200     │   หน้าเว็บ (อยู่คนละ repo)
│  water-bill-web     │   ../../WaterWeb/water-bill-web
└──────────┬──────────┘
           │ HTTP + JSON
           ▼
┌─────────────────────┐  multipart/form-data  ┌──────────────────────┐
│  NestJS   :3000     │ ────────────────────► │  FastAPI   :8000     │
│  water-bill-service │ ◄──────────────────── │  meter-vision-service│
└──────────┬──────────┘         JSON          │  (YOLO best.pt)      │
           │ TypeORM                          └──────────────────────┘
           ▼
┌─────────────────────┐
│  MySQL    :3306     │
│  water-bill-db      │   XAMPP
└─────────────────────┘
```

| ส่วน           | โฟลเดอร์                                 | พอร์ต | ภาษา                                   |
| -------------- | ---------------------------------------- | ----- | -------------------------------------- |
| หน้าเว็บ       | `WaterWeb/water-bill-web`                | 4200  | Angular 21 (standalone, zoneless, SSR) |
| Backend        | `WaterService/water-bill-service-master` | 3000  | NestJS + TypeORM                       |
| Vision service | `WaterService/meter-vision-service`      | 8000  | Python 3.12 + FastAPI + Ultralytics    |
| ฐานข้อมูล      | XAMPP                                    | 3306  | MySQL / MariaDB                        |

## วิธีรัน (ต้องเปิด 3 อย่าง ตามลำดับนี้)

**1. MySQL** — เปิด XAMPP Control Panel แล้วกด Start ที่ MySQL

**2. Backend + Vision service** (คำสั่งเดียว รันทั้งคู่ผ่าน `concurrently`)

```powershell
cd water-bill-service
npm run start:dev
```

`npm start` และ `npm run start:dev` สตาร์ท NestJS (`[api]`) พร้อม FastAPI (`[vision]`) เสมอ ต่างกันแค่ `start:dev` เปิด `--watch` ให้ด้วย
ทั้งคู่มี `prestart` / `prestart:dev` เคลียร์พอร์ต 3000 กับ 8000 ให้ก่อนอัตโนมัติ
(อยากรันแยกก็ยังทำได้: `npm run start:api` และ `npm run start:vision`)

### venv ของ vision service ติดตั้งให้เอง

`scripts/start-vision.ts` หา Python จาก `meter-vision-service/venv` (หรือ `.venv`) รองรับทั้ง Windows และ macOS/Linux
**ถ้ายังไม่มี venv จะสร้างให้เองแล้ว `pip install -r requirements.txt` ต่อทันที** — ครั้งแรกใช้เวลานาน เพราะ `ultralytics` ลาก `torch` มาด้วยราว 2GB ครั้งต่อไปเจอ venv เดิมแล้วสตาร์ทเลย

ถ้าติดตั้งไม่สำเร็จ (ไม่มี Python ในเครื่อง หรือ pip พัง) สคริปต์จะพิมพ์วิธีติดตั้งเองแล้วจบด้วย exit code 0 **โดยเจตนา** — เพราะ `concurrently` ตั้ง `--kill-others-on-fail` ไว้ ถ้าจบแบบ error NestJS ที่รันคู่กันจะถูกฆ่าตามไปด้วย ผลคือ backend รันต่อได้ปกติ เสียแค่หน้าสแกนมิเตอร์

> ⚠️ `torch` ยังไม่มี wheel ให้ Python รุ่นใหม่สุดเสมอไป ถ้า pip ล้มตอน bootstrap ให้สร้าง venv ด้วย **Python 3.12** เอง:
> ```powershell
> cd meter-vision-service
> py -3.12 -m venv venv
> .\venv\Scripts\Activate.ps1
> pip install -r requirements.txt
> ```

**3. หน้าเว็บ**

```powershell
cd ..\..\WaterWeb\water-bill-web
ng serve
```

เปิด `http://localhost:4200` — Swagger ของ backend อยู่ที่ `http://localhost:3000/api`

## ตั้งค่าฐานข้อมูลครั้งแรก

สร้าง database ชื่อ `water-bill-db` แล้ว import dump:

```powershell
& "C:\xampp\mysql\bin\mysql.exe" -u root water-bill-db < db\water-bill-db.sql
```

จากนั้นรัน migration ที่ยังไม่ได้รวมเข้า dump (ดูหัวข้อถัดไป) แล้วปิดท้ายด้วย `npm run seed:admin`

`synchronize` ถูกตั้งเป็น `false` ใน `src/app.module.ts` และ **ควรปล่อยไว้แบบนั้น** — ดูหัวข้อ "ปัญหาที่ยังค้าง" ว่าทำไมการเปิดมันถึงอันตราย

### Migration ที่ต้องรันเอง

ไม่มีตารางบันทึกว่ารัน migration ไหนไปแล้ว (ไม่ได้ใช้ TypeORM migration) ต้องเทียบ entity กับ DB เอง — ทุกไฟล์รันซ้ำไม่ได้ ถ้าคอลัมน์มีอยู่แล้วจะ error ให้ข้ามไป

| ไฟล์                              | ทำอะไร                                                            | ต้องรันเมื่อ                          |
| --------------------------------- | ----------------------------------------------------------------- | ------------------------------------- |
| `db/migrate-longitude-precision.sql` | ขยาย `members.longitude` เป็น `decimal(11,8)`                  | ฐานข้อมูลที่ import จาก dump รุ่นเก่า |
| `db/migrate-reading-location.sql`    | เพิ่ม `latitude` / `longitude` / `gps_accuracy_m` / `captured_at` ให้ `meter_readings` | ทุกฐานข้อมูล (ยังไม่อยู่ใน dump)      |
| `db/migrate-meter-digits.sql`        | เพิ่ม `meter_digits` ให้ `meter_readings` (ด่านกัน OCR อ่านหลักหาย/เกิน) | ทุกฐานข้อมูล (ยังไม่อยู่ใน dump)      |

```powershell
& "C:\xampp\mysql\bin\mysql.exe" -u root water-bill-db < db\migrate-reading-location.sql
& "C:\xampp\mysql\bin\mysql.exe" -u root water-bill-db < db\migrate-meter-digits.sql
```

**เรื่อง `decimal(11,8)`** — ลองจิจูดของไทยอยู่ที่ 97–106 ซึ่งเป็นเลข 3 หลักหน้าจุดทศนิยม แต่ `decimal(10,8)` เหลือที่ให้แค่ 2 หลัก (สูงสุด `99.99999999`) ทุกจังหวัดตั้งแต่ลองจิจูด 100 ขึ้นไป (กรุงเทพ 100.5, โคราช 102.1) จึงบันทึกไม่ได้ — strict mode เด้ง error 1264, ไม่ strict ก็โดนตัดเหลือ `99.99999999` เงียบ ๆ พิกัดเพี้ยนไปหลายร้อยกิโลเมตร
(ละติจูดไทย 5–20 เป็นเลข 2 หลัก ใช้ `decimal(10,8)` ได้ตามเดิม)

ท้าย `migrate-longitude-precision.sql` มีคิวรีไล่ดูว่ามีบ้านไหนโดนตัดไปแล้วบ้าง — ค่าที่โดนตัดกู้คืนไม่ได้ ต้องกรอกพิกัดใหม่

### ตาราง `admin` ในdump เก่ากว่า entity

ตาราง `admin` ใน `db/water-bill-db.sql` เก่ากว่า `AdminEntity` อยู่ 5 คอลัมน์ **และไม่มีแถวแอดมินเลยสักแถว** หลัง import ให้รัน:

```powershell

```

สคริปต์นี้เติมคอลัมน์ที่ขาด (เพิ่มอย่างเดียว ไม่ลบของเดิม) ขยาย `password` ให้พอกับ bcrypt hash 60 ตัว แล้วสร้างแอดมินเริ่มต้นให้ รันซ้ำได้ไม่พัง
เปลี่ยนบัญชีเริ่มต้นได้ด้วย `SEED_ADMIN_*` ใน `.env` (ดู `.env.example`)

## การเข้าสู่ระบบ

ระบบมีผู้ใช้ 2 ชนิด แยก token คนละชุด

| ชนิด            | สมัคร                   | ล็อกอินด้วย | เห็นอะไร                                    |
| --------------- | ----------------------- | ----------- | ------------------------------------------- |
| แอดมิน (หมู่บ้าน) | `POST /auth/register`   | อีเมล       | ทุกอย่าง                                    |
| ลูกบ้าน          | `POST /auth/member/register` | เบอร์โทร | เฉพาะบ้านตัวเอง (`/me/*`)                   |

ลูกบ้านสมัครได้เฉพาะเบอร์ที่มีบ้านลงทะเบียนไว้แล้วในระบบ — ผูกผ่านตาราง `account_members` (บัญชีเดียวดูได้หลายบ้าน)

บัญชีแอดมินทดสอบ: `somying@example.com` / `password123` (สร้างด้วย `npm run seed:admin` — ไม่ได้มากับ dump)

หน้าเว็บเก็บ session ไว้ใน `localStorage` (key `water-bill.admin`) และมี `authGuard` กันหน้าที่ต้องล็อกอิน

ฝั่ง API ป้องกันด้วย `JwtAuthGuard` + `RolesGuard` ที่ลงทะเบียนเป็น `APP_GUARD` ระดับ global ใน `app.module.ts` — **ทุก route ปิดเป็นค่าเริ่มต้น** route ที่ตั้งใจเปิดสาธารณะต้องแปะ `@Public()` เอง (ลืมแปะ = ปิด ซึ่งปลอดภัยกว่าลืมแปะ = เปิดทิ้ง)

### Vision service — `http://localhost:8000`

| Method | Path      | หมายเหตุ                                                 |
| ------ | --------- | -------------------------------------------------------- |
| GET    | `/health` | เช็คสถานะ + ดู class ของโมเดล                            |
| POST   | `/detect` | อัปโหลดรูป (multipart field ชื่อ `file`) → คืนเลขมิเตอร์ |

โมเดลมี 12 class: `0`–`9` คือตัวเลขแต่ละหลัก, `10` = `border_decimal_point`, `11` = `border_water_meter_number`

```json
{
  "success": true,
  "read_unit": "00025",
  "integer_part": "00025",
  "decimal_part": "312",
  "full_reading": "00025312",
  "confidence": 0.91
}
```

`POST /meter-readings/ocr-upload` คืนผลชุดนี้ต่อให้หน้าเว็บ พร้อม `meter_digits` (จำนวนหลักที่นับจาก `integer_part`) และ `photo_taken` (EXIF) ที่ backend เติมให้ — **หน้าเว็บต้องส่ง `meter_digits` ต่อไปกับ `POST /bills/scan`** ไม่งั้นด่านจำนวนหลักจะไม่ทำงาน

> ⚠️ **backend ใช้ `integer_part` เท่านั้น** — เลขสีดำบนหน้าปัด (ลูกบาศก์เมตร)
> `full_reading` รวมเลขทศนิยม (เข็มแดง) มาด้วย มิเตอร์ที่อ่านได้ 25.312 จะกลายเป็น 25312 ใหญ่เกินจริง 1,000 เท่า
> ตัวเลขนี้ถูกส่งต่อเป็น `current_unit` ตรง ๆ อ่านผิดจึงเท่ากับยอดเงินผิดทันที

## จับคู่รูปกับบ้าน — `POST /bills/scan-batch`

อัปรูปมิเตอร์ทีเดียวได้สูงสุด **30 ใบ** ระบบ OCR ทีละใบแล้วเดาว่าใบไหนเป็นของบ้านหลังไหน

> **ไม่เขียนอะไรลงฐานข้อมูลเลย** — คืนแค่ข้อเสนอพร้อมเหตุผล เมื่อคนตรวจกดยืนยันแล้วหน้าเว็บต้องยิง `POST /bills/scan` ทีละหลัง เพราะด่านกันข้อมูลผิดทั้งหมดอยู่ที่นั่น

### ทำไมจับคู่ด้วย "เลขมิเตอร์" ไม่ใช่ GPS

เลขมิเตอร์เป็นยอดสะสมตั้งแต่วันติดตั้ง ไม่ได้รีเซ็ตทุกเดือน แต่ละบ้านจึงมีเลขที่ห่างกันมากตามอายุการใช้งาน (บ้านหนึ่ง 1,250 อีกบ้าน 3,891) เลขที่อ่านได้จากรูปจึงชี้กลับไปหาบ้านต้นทางได้เองด้วยเงื่อนไขสองข้อ:

1. **ห้ามติดลบ** — มิเตอร์เดินหน้าอย่างเดียว เลขใหม่ต้อง ≥ เลขตั้งต้นของบ้านนั้น (บ้านที่ทำให้ติดลบถูกตัดทิ้ง)
2. **หน่วยที่ใช้ต้องสมเหตุสมผล** — เทียบกับที่บ้านหลังนั้นเคยใช้จริง ยิ่งใกล้ค่าเฉลี่ยยิ่งได้คะแนนสูง

เกณฑ์ตัดใช้ค่าเดียวกับ `assertUsageLooksSane()` ของ `BillsService` เป๊ะ ๆ (`USAGE_HARD_CAP` / `USAGE_SPIKE_RATIO` / `USAGE_SPIKE_FLOOR` เป็น static บน `BillsService`) ไม่งั้นหน้านี้จะเสนอบ้านที่พอกดยืนยันจริงแล้วโดนตีกลับเป็น 409

GPS ทำแบบนี้ไม่ได้ เพราะบ้านในหมู่บ้านห่างกัน 8–20 เมตร ขณะที่ GPS มือถือคลาดเคลื่อน 10–30 เมตรเป็นปกติ — รัศมีที่กว้างพอจะไม่ปฏิเสธคนถ่ายถูกบ้าน ย่อมครอบบ้านข้างเคียงไปด้วยเสมอ

| ค่า         | แปลว่า                                                              |
| ----------- | ------------------------------------------------------------------- |
| `high`      | อันดับ 1 นำอันดับ 2 เกิน 2 เท่า และคะแนน ≥ 0.4 — หน่วยใกล้ค่าเฉลี่ยมาก |
| `medium`    | นำชัดแต่คะแนนไม่สูง หรือบ้านใหม่ที่ยังไม่มีประวัติให้เทียบ            |
| `ambiguous` | เข้าได้หลายบ้านพอ ๆ กัน — `suggestion` เป็น `null` ให้คนเลือกเอง       |
| `none`      | อ่านเลขไม่ได้ หรือไม่เข้ากับบ้านหลังไหนเลย                            |

ทุกใบคืน `reason` เป็นภาษาไทยที่อธิบายว่าทำไมถึงตัดสินแบบนั้น พร้อม `candidates` 5 อันดับแรกให้ทำ dropdown

vision service ล่มไม่ทำให้ทั้งชุด 30 ใบพัง — ใบที่อ่านไม่ได้ตกเป็น `none` แล้วเดินหน้าใบถัดไปต่อ

### ตรวจข้ามใบ: หลายรูปชี้บ้านเดียวกัน

การให้คะแนนมองทีละใบ จึงไม่รู้ว่าใบอื่นเสนอบ้านอะไรไปแล้ว — รูปหลายใบที่เลขมิเตอร์ใกล้กันจะถูกเสนอให้บ้านหลังเดียวกันทั้งหมดอย่างมั่นใจ (`high` ทุกใบ) แล้วไปแตกตอนกดยืนยันทีละใบ: ใบแรกออกบิลผ่าน ที่เหลือโดน 409 บิลซ้ำ และถ้าเผลอกด "จดทับ" ไปเรื่อย ๆ จะเหลือบิลใบเดียว ส่วนบ้านที่เหลือไม่มีบิล

`flagDuplicateSuggestions()` จึงตรวจอีกรอบหลังอ่านครบทุกใบ — ถ้ามี ≥ 2 ใบชี้บ้านเดียวกัน **ลดทุกใบในกลุ่มเป็น `ambiguous`** พร้อมบอกว่าใบไหนชนกับใบไหน:

```json
{
  "index": 0,
  "confidence": "ambiguous",
  "suggestion": null,
  "conflicts_with": [1, 2],
  "reason": "รูปที่ 1, 2, 3 ถูกเสนอให้บ้าน 12/3 เหมือนกันทั้งหมด แต่ 1 บ้านมีบิลได้เดือนละใบเดียว ..."
}
```

`candidates` ยังอยู่ครบให้คนเลือกเอง และ `summary.conflicts` บอกจำนวนใบที่ถูกลดชั้นด้วยเหตุนี้

**ทำไมลดทุกใบ ไม่เก็บใบที่คะแนนดีที่สุดไว้** — เพราะไม่มีข้อมูลพอจะรู้ว่าใบไหนถูก คะแนนที่สูงกว่าเล็กน้อยไม่ได้แปลว่าใบนั้นเป็นของบ้านหลังนี้จริง อาจเป็นรูปเดียวกันถ่ายซ้ำ หรือ OCR อ่านผิดทั้งกอง การเลือกใบที่คะแนนสูงสุดไว้คือการเดาที่ดูน่าเชื่อถือ ซึ่งอันตรายกว่าการบอกว่าไม่รู้ (แนวเดียวกับ `gpsTiebreak` ที่ยอมคืน `null` เมื่อข้อมูลไม่พอ)

### บ้านที่ออกบิลเดือนนี้ไปแล้ว

คะแนนถูกคูณด้วย `ALREADY_BILLED_PENALTY = 0.3` — ไม่ตัดทิ้ง เพราะจดผิดแล้วมาแก้เป็นเรื่องปกติ แต่ต้องไม่ชนะบ้านที่ยังไม่มีบิลซึ่งเข้าเค้าพอ ๆ กัน ไม่งั้นรูปของบ้านที่ยังไม่ได้ออกบิลจะถูกเสนอให้ไปทับใบของบ้านข้าง ๆ

ถ้าสุดท้ายยังถูกเสนออยู่ จะมีคำเตือนติดไปด้วยว่าการยืนยันคือการจดทับของเดิม

### บทบาทของ GPS: ใช้ตัดสินเสมอกันเท่านั้น

พิกัดถูกอ่านจาก EXIF ของไฟล์รูป (`PhotoMetadataService`) และเอามาใช้ **แค่ 2 อย่าง**:

- **ตัดสินตอนเสมอ** (`gpsTiebreak`) — ยอมตัดสินเฉพาะตอนที่ผลต่างชัดจริง คือหลังหนึ่งอยู่ในระยะ ≤ 50 ม. ขณะที่อีกหลังไกลเกิน 150 ม. ถ้าทั้งคู่ใกล้พอ ๆ กัน (ซึ่งเป็นเรื่องปกติ) ต้องคืน `null` ให้คนเลือกเอง และผลลัพธ์ได้แค่ `medium` ไม่มีทางเป็น `high`
- **เตือน** — จุดที่ถ่ายห่างจากบ้านที่เสนอเกิน 150 ม. หรือวันในรูปไม่ใช่เดือนที่กำลังออกบิล จะขึ้นใน `warnings` แต่ไม่บล็อก (นาฬิกากล้องตั้งผิดเจอบ่อย และ EXIF ไม่มี timezone ติดมาด้วย)

**พิกัดอ้างอิงของบ้านใช้ 2 แหล่ง เรียงตามความน่าเชื่อถือ:**

1. **พิกัดที่เรียนรู้จากการจดจริง** (`learnedMeterLocations`) — มัธยฐานของพิกัดทุกครั้งที่เคยไปยืนจดบ้านหลังนั้น ต้องมีอย่างน้อย 2 ครั้งถึงจะเชื่อ
   ใช้ **มัธยฐาน ไม่ใช่ค่าเฉลี่ย** เพราะครั้งที่ GPS ยังไม่ fix จะให้พิกัดผิดไปเป็นกิโล ค่าเฉลี่ยจะถูกลากไปทั้งชุดจากค่าเดียว
2. **`members.latitude/longitude` ในทะเบียน** — ใช้เมื่อยังมีประวัติไม่พอ มักมาจากการจิ้มหมุดบนแผนที่ (กลางหลังคา) ขณะที่มิเตอร์อยู่ริมรั้ว จึงมีระยะเหลื่อมติดอยู่ 10–15 ม. ทุกครั้ง พอ ๆ กับระยะห่างระหว่างบ้าน

ข้อ 1 ดีกว่าเพราะทั้งจุดอ้างอิงและจุดที่วัดมาจากเซนเซอร์เดียวกัน ยืนที่เดียวกัน ความคลาดเคลื่อนแบบคงที่จึงหักล้างกันเอง เหลือแต่ error สุ่มที่เฉลี่ยทิ้งได้

### EXIF หายง่ายมาก

ในระบบนี้มีจุดที่ลบ EXIF ทิ้งอยู่ 2 จุด:

1. หน้าเว็บย่อ/ครอปรูปด้วย canvas ก่อนส่ง — canvas วาดพิกเซลใหม่ metadata ไม่ติดไปด้วย
2. `MeterPhotoService.save()` ผ่าน `sharp().rotate().jpeg()` — sharp ทิ้ง metadata เป็นค่าเริ่มต้น

`PhotoMetadataService.read()` จึงต้องถูกเรียกกับ buffer ที่รับมาจาก multipart **ก่อน** ส่งต่อให้ใครทั้งสิ้น (รวมถึงก่อนยิงไป vision service เผื่อฝั่งนั้นล่ม) ถ้าได้ `has_exif: false` แปลว่ารูปผ่านการประมวลผลมาแล้ว ไม่ใช่ว่าไม่มีข้อมูลตั้งแต่ต้น

> **ทางที่ดีกว่าคืออย่าพึ่ง EXIF** — `POST /bills/scan` รับ `latitude` / `longitude` / `gps_accuracy_m` / `captured_at` เป็นฟิลด์ตรง ๆ ใน body ให้หน้าเว็บส่งค่าจาก `navigator.geolocation.getCurrentPosition()` ตอนกดชัตเตอร์แทน ได้ `accuracy` แถมมาด้วยซึ่ง EXIF ไม่มีให้ และไม่ต้องพึ่งว่าผู้ใช้เปิด geotag ไว้หรือเปล่า (ส่วนใหญ่ปิด)

## ลงทะเบียนบ้านแบบยืนที่มิเตอร์ — `POST /member/register-onsite`

ของเดิม (`POST /member/create`) กรอกฟอร์มจากที่ทำการ ทำให้เกิดปัญหาสองอย่าง:

1. พิกัดในทะเบียนคือกลางหลังคา แต่ตอนจดมิเตอร์พนักงานยืนริมรั้ว — เหลื่อมกัน 10–15 ม. ทุกครั้ง แยกบ้านไม่ออก
2. **ไม่เคยบันทึกเลขมิเตอร์ตั้งต้น** → บิลใบแรกคิดจาก 0 บ้านที่มิเตอร์เดินมาแล้ว 800 หน่วยก่อนเข้าระบบจะโดนเก็บย้อนหลังทั้งก้อนโดยไม่มีใครเตือน

แบบใหม่บันทึกตอนยืนอยู่หน้ามิเตอร์จริง แก้ทั้งสองข้อพร้อมกัน — สร้างทั้ง `members` และการจดครั้งแรกใน `meter_readings` ในทรานแซกชันเดียว การจดครั้งแรกนี้คือสิ่งที่ `getPreviousUnit()` มองหาเป็นลำดับที่ 2 (`source: 'registration'`) อยู่แล้ว

**ด่านตรวจ:**

- ต้องส่งพิกัดมาเสมอ (ไม่ใช่ optional เหมือนของเดิม) และต้องมาจาก `navigator.geolocation` ตอนยืนอยู่จริง ห้ามจิ้มจากแผนที่
- `gps_accuracy_m > 50` → ปฏิเสธ ให้รอสัญญาณนิ่งแล้วกดใหม่ (พิกัดที่ห่วยกว่านั้นรับไว้ก็ไปทำให้ค่ามัธยฐานเพี้ยน แล้วหลอกให้ระบบคิดว่ามีพิกัดอ้างอิงทั้งที่ใช้จริงไม่ได้)
- `initial_meter_unit` ต้องเป็นจำนวนเต็มไม่ติดลบ
- บ้านเลขที่ห้ามซ้ำ
- รูปหลักฐานเขียนลงดิสก์ก่อนเข้าทรานแซกชัน ถ้าทรานแซกชันล้มจะลบไฟล์ทิ้งให้ (การเขียนดิสก์ย้อนกลับพร้อม rollback ไม่ได้)

## เลขตั้งต้นที่ใช้คิดหน่วยน้ำ

`getPreviousUnit()` เป็น **จุดเดียวในระบบที่ตัดสินเรื่องนี้** ทั้งหน้าจอและตอนออกบิลจริงเรียกตัวเดียวกัน ตัวเลขบนจอกับยอดที่ออกจริงจึงตรงกันเสมอ

| ลำดับ | แหล่ง                                          | `source`         |
| ----- | ---------------------------------------------- | ---------------- |
| 1     | เลขปิดของบิลใบล่าสุดที่เดือนเก่ากว่า            | `'bill'`         |
| 2     | เลขมิเตอร์ ณ วันลงทะเบียนบ้าน (การจดครั้งแรกสุด) | `'registration'` |
| 3     | ไม่มีทั้งคู่ → 0                                | `'none'`         |

กฎชุดนี้อยู่ใน `resolvePreviousUnit()` ซึ่งรับข้อมูลที่โหลดมาแล้วเข้าไปตรง ๆ ไม่ยิงคิวรีเอง ทั้งแบบรายบ้าน (`getPreviousUnit`) และแบบยกชุด (`previousUnitsForMembers` ที่ scan-batch ใช้) จึงใช้กฎเดียวกันจริง ๆ

## ด่านกันข้อมูลผิดตอนออกบิล

ทั้งหมดอยู่ใน `bills.service.ts` และทำงานก่อนเขียนฐานข้อมูลเสมอ — `prepareBill()` ตรวจให้จบก่อน แล้วค่อยเขียนทั้ง `meter_readings` และ `bills` ในทรานแซกชันเดียว

| เคส                                       | เกิดอะไรขึ้น                                                        |
| ----------------------------------------- | ------------------------------------------------------------------- |
| เลขมิเตอร์น้อยกว่าเลขตั้งต้นเดือนก่อน      | 400 — บอกทั้งเลขที่จดและเลขตั้งต้น พร้อมทางออกเรื่องเปลี่ยนมิเตอร์  |
| เปลี่ยนมิเตอร์ใหม่ / มิเตอร์วนรอบ 99999→0  | กด `confirm_meter_reset` ผ่านได้ เริ่มนับจาก 0 ให้                  |
| หน่วยน้ำสูงผิดปกติ                         | 409 ต้องกด `confirm_high_usage` ยืนยัน ไม่บล็อกตาย                  |
| **จำนวนหลักบนหน้าปัดไม่ตรงกับที่เคยอ่านได้** | 409 ต้องกด `confirm_digit_change` — จับ OCR อ่านหลักหาย/เกิน        |
| ออกบิลซ้ำเดือนเดิม                         | 409 ต้องกด `replace` จดทับ — ถ้าบิลนั้นจ่ายแล้วห้ามทับเด็ดขาด        |
| ออกบิลย้อนหลังทับหน้าใบที่ใหม่กว่า          | 409 ต้องลบใบที่ใหม่กว่าก่อน (ไม่งั้นใบใหม่จะมีเลขตั้งต้นผิดทันที)   |
| เดือน/ปีของบิลไม่ใช่ 01-12 หรือปีเพี้ยน     | 400 — ถ้าปล่อยผ่าน `monthKey()` จะได้ `NaN` แล้วด่านเทียบเดือนหลุดหมด |
| `reading_date` อ่านไม่ออก / เป็นอนาคต       | 400                                                                 |
| `reading_date` ห่างจากเดือนบิลเกิน 15 วัน   | 400 ให้แก้วันที่จด หรือเปลี่ยนเดือนบิลให้ตรงกัน                     |
| พิกัดนอกช่วง (พิมพ์ผิด / สลับ lat-lng)      | 400 — ไม่ปล่อยไปพังที่ MySQL เป็น error 1264                        |
| `captured_at` ที่ไม่ใช่วันที่                | ถือเป็น `null` ไม่บล็อก (เป็นข้อมูลประกอบ ไม่มีผลต่อยอดเงิน)        |
| ลบบิลที่ `Paid` แล้ว                        | 409 — ลบแล้วหายทั้งบิล การจดมิเตอร์ และไฟล์รูปหลักฐาน กู้ไม่ได้      |
| ไม่แนบรูปมิเตอร์                           | ออกบิลได้ปกติ — รูปเป็น optional                                    |

**"สูงผิดปกติ" คิดจาก** — บ้านที่มีประวัติ: `หน่วยเดือนนี้ > ค่าเฉลี่ยทุกบิลที่ผ่านมา × 5` **และ** `> 50 หน่วย` (เงื่อนไข 50 กันบ้านที่ปกติใช้ 2 หน่วยแล้วเด้งทุกเดือน) / บ้านใหม่ที่ยังไม่มีประวัติ: `> 1000 หน่วย` ตายตัว

**ด่านจำนวนหลักทำงานยังไง** — มิเตอร์ตัวเดิมมีจำนวนหลักคงที่ตลอดอายุการใช้งาน ระบบเทียบ `meter_digits` ที่ OCR ส่งมากับค่าที่บ้านหลังนี้เคยอ่านได้ล่าสุด ต่างเมื่อไหร่แปลว่าอ่านหลักหายหรือหลักเกิน

ด่านนี้ **ไม่พึ่งประวัติการใช้น้ำเลย** จึงจับเคสที่ด่านหน่วยพุ่งปล่อยผ่านได้ — บ้านที่ยังไม่มีบิลใช้เพดาน 1,000 หน่วยซึ่งหลวมพอให้เลขที่เกินมาหนึ่งหลักลอดไปได้ และบ้านที่ปกติใช้เยอะอยู่แล้วเพดาน "เฉลี่ย × 5" ก็สูงตามไปด้วย

จำนวนหลักนับจาก **string ดิบ** ก่อนแปลงเป็นตัวเลข — `00025` คือ 5 หลัก ไม่ใช่ 2 เพราะศูนย์นำหน้าคือหลักที่มีอยู่จริงบนหน้าปัด ถ้านับจากตัวเลขที่แปลงแล้วค่าจะเปลี่ยนไปมาตามที่มิเตอร์เดินไปถึง แล้วเทียบข้ามเดือนไม่ได้เลย

ไม่ส่ง `meter_digits` มา (กรอกเลขเอง ไม่ได้ผ่าน OCR) จะข้ามด่านนี้ไป — คอลัมน์เก็บเป็น `NULL` และไม่ถูกนับเป็นค่าอ้างอิงของเดือนถัดไป

**เปลี่ยนมิเตอร์แล้วน้ำที่ใช้ก่อนถอดไปไหน** — ส่ง `old_meter_final_unit` (เลขปิดของตัวเก่า ณ วันถอด) มาด้วย ระบบจะบวกส่วนต่างเข้าไปในบิลนี้ให้ครบ ไม่ส่งมาก็คิดเฉพาะมิเตอร์ตัวใหม่ — คิดขาดดีกว่าคิดเกิน เพราะลูกบ้านเป็นฝ่ายจ่าย

**ลบบิล / ลบบ้าน จะเก็บกวาดไฟล์รูปให้ด้วย** — ลบทีหลัง commit สำเร็จเสมอ เพราะการลบไฟล์ย้อนกลับพร้อม rollback ไม่ได้

## ปัญหาที่ยังค้าง

### 🔴 อย่าเปิด `synchronize: true`

`app.module.ts` ตั้ง `synchronize: false` ไว้ ถ้าเปิดเป็น `true` TypeORM จะเห็นว่าชื่อคอลัมน์ไม่ตรง (`creat_date` ไม่มี e, `members_id1` มี 1 ต่อท้าย, `craeta_date` / `craete_by` สะกดสลับ) แล้ว **drop คอลัมน์เก่าทิ้งพร้อม FK แล้วสร้างชื่อใหม่** schema จะเพี้ยนจาก `db/water-bill-db.sql` ถาวร

(ตาราง `provinces` / `districts` / `subdistricts` ที่มีข้อมูลรวม 8,369 แถว ไม่มี entity รองรับ TypeORM จึงไม่แตะ — ข้อมูลอ้างอิงพวกนั้นปลอดภัย)

### 🟡 ไม่มี global `ValidationPipe`

`class-validator` อยู่ใน dependencies แล้วแต่ DTO ยังไม่มี decorator และ `main.ts` ยังไม่เปิด pipe

ตอนนี้แต่ละ service ต้องดักเองด้วยมือ — `auth.service.ts` เช็ค `email`/`password`, `member.service.ts` เช็คช่วงพิกัดและ accuracy, `bills.service.ts` เช็คเดือน/ปี/วันที่จด/พิกัด, `reports.service.ts` เช็คหมวดหมู่ ยิ่งเพิ่ม endpoint ยิ่งลืม ควรเปิด global `ValidationPipe` แล้วย้ายกฎพวกนี้ไปไว้ที่ DTO

### 🟡 ตาราง `water_rates` ว่าง

`GET /water-rates/active` คืน 200 พร้อม body ว่าง ต้องมีอัตราค่าน้ำอย่างน้อย 1 แถวถึงจะคิดบิลได้

### 🟡 `CONF_THRESHOLD` ในโค้ดกับใน `meter-vision-service/README.md` ไม่ตรงกัน

โค้ดตั้ง `0.8` แต่ README ของ service นั้นบอก `0.35` ค่า 0.8 สูงมากสำหรับการตรวจเลขเล็ก ๆ บนหน้าปัด อาจทำให้ `/detect` คืน "ไม่พบตัวเลขมิเตอร์" บ่อยเกินจริง ปรับได้โดยไม่ต้องแก้โค้ด: `$env:CONF_THRESHOLD="0.35"` ก่อนรัน

### ช่องที่ยังหลุดอยู่

- **OCR อ่านผิดนิดเดียวโดยจำนวนหลักไม่เปลี่ยน** (1250 → 1258) ยังทะลุทุกด่าน ออกบิลเงียบ ๆ — ด่านจำนวนหลักจับได้เฉพาะหลักหาย/หลักเกิน ส่วนหลักที่อ่านผิดค่าต้องดูที่ confidence ซึ่งตอนนี้ `main.py` ส่งมาเป็น **ค่าเฉลี่ยรวม** หลักเดียวที่มั่นใจ 0.4 จึงถูกกลบด้วยหลักอื่นที่ 0.95 — ควรส่ง confidence ของหลักที่ต่ำที่สุดมาด้วย และตั้งเกณฑ์ของหลักหน้า (พัน/หมื่น) ให้สูงกว่าหลักหลัง เพราะผิดแล้วเงินคลาดคนละระดับ
- **บ้านที่ยังไม่เคยจดผ่าน OCR ไม่มีจำนวนหลักให้เทียบ** ด่านจำนวนหลักจึงเริ่มทำงานตั้งแต่การจดด้วย OCR ครั้งที่สองเป็นต้นไป — ถ้าอยากให้ครอบตั้งแต่ใบแรก ต้องบันทึกจำนวนหลักตอน `register-onsite`
- **ค่าเฉลี่ยของด่านหน่วยพุ่งใช้บิลทุกใบตลอดกาล** บ้านที่เคยท่อแตกครั้งเดียวจะดันค่าเฉลี่ยขึ้นถาวร ด่านอ่อนลงเรื่อย ๆ — ควรใช้ 3-6 เดือนล่าสุด หรือใช้ median (แบบเดียวกับที่ `learnedMeterLocations` ใช้อยู่แล้ว)
- **เดือนที่ข้ามไปไม่มีใครรู้** ไม่มีบิล ก.ค. แล้วออกบิล ส.ค. จะได้หน่วยสองเดือนรวมกันโดยบิลไม่บอกว่าคาบกี่เดือน
- **`Overdue` ต้องกดเปลี่ยนสถานะเอง** ไม่มี `due_date` ไม่มีค่าปรับ ไม่มีการทบยอด — บ้านค้าง 6 เดือนเห็นเป็นบิล `Pending` 6 ใบแยกกัน ต้องนับเอง
- **พิกัดที่ตรงกันเป๊ะทุกทศนิยมระหว่างการจดสองเดือน = สัญญาณว่ารูปถูกใช้ซ้ำ** GPS จริงไม่เคยให้ค่าเดิมเป๊ะสองครั้ง — ตอนนี้เก็บ `captured_at` ไว้แล้วแต่ยังไม่มีโค้ดไหนไล่ตรวจเรื่องนี้

## จุดที่มักสะดุด

**`EADDRINUSE: address already in use :::3000`** — `npm run start:dev` แตก process ลูกเป็น `node dist/main` (และ `python.exe` สำหรับ vision service) การกด Ctrl+C หรือปิด terminal บางครั้งฆ่าแค่ตัวแม่ ตัวลูกยังถือพอร์ตอยู่

`prestart` / `prestart:dev` จะรัน `scripts/free-ports.ts` เคลียร์พอร์ต 3000 กับ 8000 ให้อัตโนมัติทุกครั้งก่อนสตาร์ท (ทั้ง `npm start` และ `npm run start:dev`) ปกติจึงไม่ควรเจอ error นี้ ถ้าอยากเคลียร์เองแยก ๆ ใช้ `npm run free-ports`

**`ไม่พบ JWT_SECRET ใน .env`** — แอปตั้งใจล้มตั้งแต่ตอน boot คัดลอก `.env.example` เป็น `.env` แล้วใส่ค่าสุ่มของตัวเอง

**`Unknown column 'MeterReadingEntity.latitude'`** — ยังไม่ได้รัน `db/migrate-reading-location.sql`

**`Unknown column 'MeterReadingEntity.meter_digits'`** — ยังไม่ได้รัน `db/migrate-meter-digits.sql`

**ต้องเปิด MySQL ก่อน backend เสมอ** ไม่งั้น TypeORM ต่อไม่ติดตอน bootstrap

**Vision service ใช้เวลาโหลดโมเดลตอนสตาร์ท** ให้รอ `/health` ตอบ 200 ก่อนค่อยยิงงานเข้าไป
