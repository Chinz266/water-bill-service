# การใช้งานและดูแลระบบหลังปรับปรุง

## ใช้งานบนเครื่องเดิม

หน้าเว็บยังเปิดที่ `http://localhost:4200/home` และเรียก API ที่พอร์ต 3000 เหมือนเดิม ไม่ต้องมีโดเมนหรือใบรับรองสำหรับการทดสอบบน localhost

- รูปอัปโหลด: ไม่เกิน **10 MB ต่อไฟล์**, **32 MB รวมต่อคำขอ**, **30 รูปต่อ batch**, และ **40 ล้านพิกเซลต่อรูป**
- API ตรวจข้อมูลภาพจริงหลังรับไฟล์ ไม่เชื่อเฉพาะนามสกุล/MIME; จำกัดจำนวนไบต์ระหว่างอ่านไฟล์เข้าหน่วยความจำ
- Python จำกัด request ก่อนแยก multipart รวมถึงการส่งแบบ chunked และจำกัดไฟล์ก่อน decode
- JSON รับได้สูงสุด 4 MB เพื่อรองรับรูป data URL ที่แอปย่อแล้ว; ฟิลด์รูปยังจำกัด 3 MB
- การล็อกอินผู้ดูแลและลูกบ้านรวมกันไม่เกิน **20 ครั้งต่อนาทีต่อ IP** ตอบ 429 พร้อม Retry-After เมื่อเกิน
- บัญชีผู้ดูแลใหม่ต้องมีรหัสผ่านอย่างน้อย 8 ตัวอักษรและไม่เกิน 72 ไบต์; ล็อกอินบัญชีเดิมไม่ได้บังคับความยาวขั้นต่ำใหม่
- DTO ตรวจชนิดและขนาดของฟิลด์ที่ส่งมา ป้องกัน array/object ที่ถูกส่งแทนตัวเลขหรือข้อความ โดยยังรับ numeric string สำหรับ client เดิม ฟิลด์ที่ DTO ไม่ประกาศจะถูกตัดทิ้งแบบไม่ตอบ error ส่วนฟิลด์ที่ไม่ได้ส่ง/null ยังคงใช้กฎ required และกฎธุรกิจเดิมใน service เพื่อรองรับ partial update
- การสร้างบัญชีคัดเลือกเฉพาะชื่อ นามสกุล อีเมล และรหัสผ่าน จึงส่ง `admin_role` แทรกมายกระดับสิทธิ์ไม่ได้
- บริการ AI ไม่ติดตั้งแพ็กเกจเองขณะรับรูปแล้ว ติดตั้งจาก `requirements.txt` เท่านั้น (เพิ่ม `pi-heif` ที่ Ultralytics ใช้อ่าน HEIF)

หากเปิดผ่าน IP ในวงแลน ให้เพิ่ม origin จริง เช่น `http://192.168.1.10:4200` ใน `CORS_ORIGINS` และเพิ่ม host ใน `angular.json` จากนั้น restart API

## ตรวจสถานะ

- `GET http://localhost:3000/health`: ตัว API ทำงาน
- `GET http://localhost:3000/health/ready`: ตรวจ MySQL และ Python แยกกัน; ตอบ 503 เมื่ออย่างใดอย่างหนึ่งไม่พร้อม จำกัดเวลารอแต่ละส่วน 3 วินาที
- `GET http://localhost:8000/health`: สถานะโมเดล Python

เมื่อเชื่อมต่อ AI ไม่ได้หรือ timeout งาน OCR ตอบ 503 พร้อมข้อความภาษาไทย ส่วน API งานอื่นยังทำงานได้

## สำรองและกู้คืน

รันคำสั่งจากโฟลเดอร์ `water-bill-service`:

```powershell
npm run db:backup
```

เก็บผลใน `backups/<วันเวลา>-<รหัสสุ่ม>/` ซึ่งถูก gitignore แล้ว:

- `database.sql`: snapshot ตาราง InnoDB ด้วย mysqldump --single-transaction
- `uploads/`: สำเนารูปที่มีอยู่จริง
- `manifest.json`: จำนวนแถวทุกตาราง และ SHA-256 ของ SQL กับทุกรูป

ควรหยุดการรับข้อมูลใหม่และงานล้างรูปชั่วคราวในช่วงสำรอง เพื่อให้ SQL และไฟล์อยู่ในสถานะเดียวกัน การเทียบจำนวนแถวช่วยตรวจการเปลี่ยนแปลงบางกรณี แต่ตรวจไม่พบการแก้ค่าที่จำนวนแถวเท่าเดิม สคริปต์ไม่อ้างว่าการคัดลอกไฟล์กับ snapshot SQL เป็นธุรกรรมเดียวกัน

ตัวอย่างกู้ลงฐานใหม่:

```powershell
npm run db:restore -- "backups/<ชื่อโฟลเดอร์สำรอง>" water_bill_restore_drill
```

ต้องใช้ชื่อใหม่ขึ้นต้น `water_bill_restore_` และห้ามมีฐานชื่อนั้นอยู่แล้ว สคริปต์ตรวจ hash ก่อนเริ่ม ตรวจจำนวนแถวหลัง import และกู้รูปไปยัง `<โฟลเดอร์สำรอง>/<ชื่อฐานใหม่>/uploads` พร้อมตรวจ hash อีกครั้ง ไม่เขียนทับฐานหรือรูปที่กำลังใช้งาน หาก import ล้มจะลบเฉพาะฐานใหม่ที่คำสั่งรอบนั้นสร้างขึ้น

การย้ายกลับมาใช้งานจริงต้องหยุดบริการ ตรวจผลกู้คืน แล้วเปลี่ยน `DB_DATABASE` กับโฟลเดอร์ uploads ให้ชี้ไปยังชุดที่กู้คืน ไม่มีคำสั่งเขียนทับฐานจริงอัตโนมัติในสคริปต์นี้

MySQL CLI ใช้ค่าการเชื่อมต่อจาก `.env` โดยไม่แสดงรหัสผ่านในคำสั่งหรือเก็บใน backup ตรวจพบ XAMPP บน Windows ให้อัตโนมัติ หรือกำหนด `MYSQL_PATH` / `MYSQLDUMP_PATH` เอง รองรับตาราง InnoDB ของแอปนี้; ถ้ามี view/trigger/routine/event หรือ storage engine อื่น สคริปต์จะหยุดให้ใช้แผนสำรองของผู้ดูแลฐานข้อมูล

เก็บ backup อีกชุดบนพื้นที่สำรองที่ควบคุมสิทธิ์ได้ เพราะสำเนาบนดิสก์เดียวไม่ป้องกันดิสก์เสีย ไฟล์เหล่านี้มีข้อมูลลูกบ้านและ password hash ไม่ควรแชร์หรือ commit สคริปต์ยังไม่ได้ตั้งเวลาอัตโนมัติหรือคัดลอกไปบริการภายนอก

## ทดสอบซ้ำ

```powershell
npm test -- --runInBand
npm run test:database
```

`test:database` สำรองฐานจริง กู้เป็นฐานสุ่มใหม่ และเปิด API ทดสอบเฉพาะ loopback กับพอร์ตว่าง โดยหยุด cron ของ API ทดสอบ ทดสอบการล็อกอิน/สิทธิ์ ออกบิล รับชำระ การส่งซ้ำ และ AI ขัดข้อง แล้วลบเฉพาะฐานทดสอบนั้น ตรวจจำนวนแถวและ checksum ของฐานต้นฉบับก่อน–หลัง ผลอยู่ใน `docs/database-test-result.json`

การทดสอบรูปกู้คืนมีภาพสังเคราะห์อยู่ใน `restore-test-fixture` แยกจาก backup จริง รอบที่ตรวจนี้ฐานจริงยังไม่มีไฟล์หรือการอ้างอิงรูป จึงไม่ได้อ้างว่ากู้รูปมิเตอร์ของลูกบ้านที่มีอยู่แล้ว

จากโฟลเดอร์ `meter-vision-service`:

```powershell
.\venv\Scripts\python.exe -m unittest test_service -v
```

ชุดนี้โหลดโมเดลจริงและทดสอบภาพว่าง/ขอบเขตไฟล์/การแยกทศนิยม แต่ยังไม่ใช่การวัดความแม่นยำบนชุดภาพมิเตอร์ที่มีเลขเฉลย

## เตรียม HTTPS เมื่อนำขึ้นเซิร์ฟเวอร์

1. ตั้ง reverse proxy ให้รับ HTTPS และส่ง `/api/` ไป NestJS โดยตัด `/api` ออกจากพาธ ตั้งขนาด request สูงสุด 35 MB และส่ง IP ผู้ใช้ผ่าน proxy ที่เชื่อถือได้เท่านั้น
2. ตั้ง `NODE_ENV=production`, `HOST=127.0.0.1`, `CORS_ORIGINS=https://<โดเมนจริง>`, `SWAGGER_ENABLED=false`; ถ้า proxy อยู่เครื่องเดียวกันตั้ง `TRUST_PROXY=127.0.0.1,::1`
3. หน้าเว็บที่เปิดผ่าน HTTPS จะใช้ API `/api` บน origin เดียวกันอัตโนมัติ ถ้า API แยกโดเมน ให้ใส่ URL ใน `<meta name="water-bill-api-url" content="https://<โดเมน-api>">` ของ `index.html` ก่อนให้บริการ
4. ไม่เปิดพอร์ต MySQL/Python/API ภายในสู่อินเทอร์เน็ตโดยตรง ใช้ไฟล์ static จาก `dist/water-bill-web/browser` และตั้ง fallback ไป `index.html` สำหรับ route ของ Angular

ยังไม่ได้ติดตั้งใบรับรองหรือ deploy เพราะเครื่องนี้ใช้งาน localhost หากรัน API หลาย instance ต้องเพิ่ม rate limit แบบ shared ที่ proxy หรือ Redis แทนการใช้ตัวนับในแต่ละ process อย่างเดียว

## การตัดสินใจที่ยังคงเดิม

การล็อกอินลูกบ้านด้วยเบอร์โทรอย่างเดียวยังอยู่ตามพฤติกรรมเดิม Rate limit ไม่ได้พิสูจน์เจ้าของเบอร์ หากจะเปิดสู่อินเทอร์เน็ตควรออกแบบ OTP/PIN และขั้นตอนช่วยเหลือร่วมกับผู้ดูแลก่อน ไม่มีบริการส่ง OTP ที่ตั้งค่าในโปรเจกต์นี้

รูป `/uploads/` ยังเป็น static URL ตามเดิม หากต้องการจำกัดผู้ดูรูปต้องออกแบบสิทธิ์ของรูปที่ใช้ร่วมกันในบิล/งานรอตรวจ แล้วเปลี่ยนเป็น endpoint ตรวจสิทธิ์หรือ URL อายุสั้น
